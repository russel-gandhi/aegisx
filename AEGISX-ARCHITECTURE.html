01

What the system does

Pharmaceutical companies run software that touches how medicine gets made. Regulators — the FDA in the US, the EMA in Europe — require that this software be proven trustworthy at all times, not just on the day it was installed. That proof lives in an enormous pile of documents, test records, change tickets, incident reports and access reviews. The industry term for this regime is GxP: "good practice" regulations.

When an inspector arrives, someone has to answer questions like "show me that this system's user requirements are all traceable to executed tests" or "prove the periodic review of this system happened on schedule." Answering takes days of manual evidence-hunting across a dozen disconnected systems.

AegisX AI is a co-pilot for that job. You ask a question in plain English — "Is GXP-MFG-DEMO-01 audit ready?" — and the system investigates across its records, finds the gaps, and hands back findings that have each been independently checked against the real database and a formal rulebook before you ever see them.

02

The central idea: the AI never gets the last word

Most AI products work like this: a language model reads some documents, writes an answer, and you decide whether to believe it. That is unacceptable in a regulated setting. A model that invents a plausible-sounding regulation, or confidently states a test was executed when it wasn't, is worse than no tool at all.

AegisX is built on the opposite arrangement, which the project calls deterministic-first.

In plain English

"Deterministic" means: given the same input, you get exactly the same output, every single time, because the answer is computed by fixed rules rather than generated by a model. Ordinary arithmetic is deterministic. A language model is not.

AegisX splits the work along that line. The AI is allowed to investigate, read, and phrase things. It is never allowed to decide anything that matters.

Four kinds of decision are permanently closed to the AI, enforced structurally rather than by instruction:

  • Is this claim actually supported by evidence? — decided by fetching the real database record and running a formal policy engine over it.
  • Is this user allowed to do this? — decided by a fixed permission table in Python.
  • Is this input an attack? — decided by pattern matching and a mathematical randomness measurement.
  • What relationships exist between records? — decided by walking real foreign-key links in a graph, never by inference.

The consequence is a system that can say "I don't have enough evidence to answer that" and mean it — because that verdict is produced by a check that failed, not by a model deciding to be cautious.

04

The request pipeline

Every question travels the same fixed route through eleven stations. The route never changes shape — what changes is which of the six specialists in the middle wake up for a given question.

This is built with LangGraph, a framework for wiring AI components into a defined graph rather than letting them call each other freely. Two details matter:

  • The fan-out is genuinely parallel. The six specialists run concurrently, not one after another, so a six-agent investigation costs roughly the time of the slowest agent rather than the sum of all six.
  • Their results are merged, not overwritten. The shared state uses an accumulating merge for findings, so six agents each returning findings produce a combined list. Without this, five of the six would silently vanish — a bug that would look like a suspiciously thorough system rather than an error.
05

The eleven stations, one at a time

Every agent below has a defined job, a defined check, and — critically — a defined behaviour when something goes wrong. The failure behaviour is part of each agent's contract, not an afterthought.

C2No AI

Policy & Safety Gateway

The front door. Two checks run before anything else happens, both in plain Python with no model involved.

Permissions. A fixed table maps each of three roles to the agents it may invoke. An IT System Manager reaches all seven agents. QA/Compliance reaches A1–A6 but is structurally barred from A7, the remediation agent — the role simply isn't in that set. An Auditor reaches only A1 and A2, read-only investigation.

Injection detection. A "prompt injection" is text crafted to hijack an AI's instructions — for example, a sentence buried in an uploaded document telling the model to ignore its rules. Two independent detectors run: a pattern matcher for known jailbreak phrasings, and a Shannon entropy measurement.

Entropy measures how random a piece of text looks, in bits per character. Ordinary English sits well below 4.5; base64-encoded payloads approach 6. Any token of 12+ characters scoring above 4.5 bits is flagged, which catches attacks that have been encoded to slip past the pattern matcher. Neither leg consults a model — an attack cannot talk its way past a detector that isn't listening.

Fails closed. An unrecognised or missing role is rejected before injection detection even runs. A blocked request publishes an empty permitted-agent set, so even if the block flag were ignored downstream, the fan-out would still reach nothing.

A0

Orchestrator

Reads the question and decides which specialists are relevant — a question about access reviews shouldn't wake the incident agent. This is a single classification call to a language model, returning strict JSON naming the agents to activate.

It runs under a hard 2-second budget. Not a soft deadline: the classification task is genuinely cancelled when the timer expires.

Falls back to all six. Timeout, malformed JSON, a schema failure, an empty list, or an agent name it doesn't recognise — every failure path lands on the same result: run the full diagnostic set A1–A6. A routing decision that can't be made is never an error; it just means doing the thorough thing instead of the fast thing.

A1

System Knowledge — the document search agent

Confirms the system being asked about actually exists, then performs the full hybrid document retrieval described in section 07: semantic search, keyword search, fusion, reranking, and a relevance gate. Its output rides separate state channels from the compliance findings, so retrieved evidence and rule violations never get confused for one another.

Abstains. If the system id isn't in the database, or the database is unreachable, A1 returns a defined abstain finding rather than guessing. If retrieval produces nothing above the relevance threshold, it reports insufficient evidence rather than serving the closest bad match.

A2

Compliance & Audit Readiness — the workhorse

Runs four deterministic checks in SQL, each answering a yes/no question about real records:

  • verify_urs_approved — are the user requirements actually approved?
  • verify_periodic_eval_current — is the scheduled periodic review overdue?
  • verify_test_traceability — does every requirement link to an executed, non-draft test?
  • verify_no_stale_documents — is anything superseded or withdrawn being relied on as current evidence?

The pass/fail verdict is decided entirely by the SQL. The language model's only job is turning an already-computed gap into a readable sentence. It cannot flip a verdict, and findings are only ever assembled from checks that have already failed.

Narrates deterministically. If the model is unavailable, the gap is described with a fixed template sentence instead. The finding still exists, still carries its record ids, and is still verified downstream — only the prose is plainer.

A3

Risk

Flags risk assessments that have gone past their annual review cycle under ICH Q9(R1), the international quality risk management guideline. Computes a numeric risk score from severity and probability and classifies it.

Downgrades, then templates. If its preferred model is unavailable the router moves to the next provider; if every provider fails, a deterministic sentence is used.

A4

Change

Catches change records marked CLOSED that still have open linked actions — paperwork closed while the work underneath is unfinished. It also pulls a downstream impact summary from the evidence graph (section 10) for the change in question.

Degrades to direct metadata. If the graph can't be loaded, the check still runs against the change record's own fields.

A5

Incident

Flags P1 — highest-severity — incidents that have been open more than seven days with no root cause analysis started.

Templates on model failure, like every other specialist.

A6

Access

Two checks: access reviews overdue past their scheduled date, and orphaned privileged accounts — administrator-level accounts still active for people who have left the organisation. Each is raised as an independently verifiable finding.

Templates on model failure.

C1No AI

Evidence & Grounding Verifier — the thesis of the product

Every finding produced upstream arrives here unverified and must earn its confidence grade. Section 06 covers this station in full — it is the reason the rest of the architecture is shaped the way it is.

Never trusts by default. With no findings it returns an empty result, never a hardcoded "verified". With no database connection every finding grades INSUFFICIENT_EVIDENCE.

A7

Remediation

Drafts corrective-action narratives — CAPA, in industry terms — for findings that have already been verified. It reads C1's computed confidence grade and never re-derives one of its own, so it cannot launder an unverified claim into a proposal.

It is the one station in the whole topology permitted to generate substantial prose, and it only fires when a human explicitly asks for remediation on a finding already on screen. Asking a question never triggers it as a side effect.

Produces nothing by default. Absent an explicit remediation request, A7 returns an empty proposal list — opt-in by design.

C3No AI

Action Gateway

Sorts every proposed action into one of five categories by looking up its type in a fixed table, and each category has a fixed disposition:

CategoryWhat happens
READRuns automatically.
DRAFTSaved locally, runs automatically.
MOCK_WRITE_LOW_RISKQueued for human approval; executes as a mock once approved.
GXP_RELEVANT_WRITEQueued for approval, and even when approved it stops — real execution is out of band. The system never mutates a validated GxP record itself.
PROHIBITEDBlocked outright. Deleting an audit event or disabling the audit trail live here.

Fails closed. An action type not in the table resolves to PROHIBITED, not to the permissive default. Approval dialogs render from server-held proposal data, never from model-generated text.

06

How verification actually works

C1 is where the product's promise is kept. A finding arrives saying something like "the periodic evaluation record PE-2024-01 is overdue." C1's job is to establish whether that is true, using nothing the AI said.

Step one: fetch the real record

Each finding carries a rule id and the ids of the records it claims as evidence. C1 looks up which database table that rule concerns — from a frozen internal table, never from anything in the request — and fetches the actual row.

If the record doesn't exist, the process stops immediately and the finding grades INSUFFICIENT_EVIDENCE. No policy call is needed to know that evidence is absent.

Step two: ask the rules engine, independently

C1 assembles the real rows into the shape the policy engine expects and calls OPA over HTTP. OPA re-evaluates the rule against that raw data and returns the violations it finds. C1 then checks whether OPA independently flagged the same rule on the same record.

Why this matters

The AI said there's a violation. A separate engine, which has never seen the AI's output and is running rules written by hand, is asked the same question against the same raw data. If the two disagree, the AI loses.

Step three: score data integrity across nine dimensions

Regulators assess record quality against a framework called ALCOA+. AegisX scores every fetched record against all nine dimensions by inspecting its actual column values:

DimensionWhat the system checks on the real row
AttributableDoes a person's name attach to it — author, owner, reviewer, tester?
LegibleAre its text fields actually populated rather than blank?
ContemporaneousDoes it carry a timestamp that isn't in the future?
OriginalDoes it carry a version marker, where the table has a versioning concept?
AccurateAre its status fields set rather than null?
CompleteIs every column on the row populated?
ConsistentIs the fetched record genuinely one the finding cites — proving the right row was retrieved?
EnduringTrue by construction: the row was just read back from durable storage.
AvailableTrue by construction: it was retrieved through the same path any authorised user would use.

Step four: compute the confidence grade

The three inputs — record found, ALCOA+ score, OPA agreement — combine through fixed arithmetic. No model participates.

score = 100
if no database record → INSUFFICIENT_EVIDENCE stop here
score −= (9 − alcoa_dimensions_passed) × 10
if OPA did not corroborate → score −= 100 contradicts formal policy

score > 80  → HIGH
score ≥ 50  → MEDIUM
score > 0   → LOW
otherwise  → INSUFFICIENT_EVIDENCE

Note the shape of that penalty: failing OPA corroboration costs a full 100 points — the entire budget. A claim the formal rulebook won't confirm cannot reach any positive grade, no matter how pristine its record. That single line is the deterministic-first principle expressed as arithmetic.

Each verification also records which version of the policy bundle produced it, so a finding can always be traced back to the exact rulebook that judged it.

07

Searching the documents, from first principles

The system ingests real regulatory documents — validation reports, requirement specifications, data integrity assessments — and has to find the right passage when you ask a question. This is the part usually called RAG: Retrieval-Augmented Generation. Here is what that actually means, assuming no prior knowledge.

Getting documents in

Four formats are accepted — PDF, Word, CSV, and plain text or Markdown — up to 10 MB each. Each is parsed into blocks, and each format yields honestly different metadata: PDFs give real page numbers plus a best-effort heading guess; Word documents give real heading text but no page numbers, because the format has no reliable page model; CSVs get the filename as a section and row-block numbers as pages.

The text is then chunked: cut into overlapping pieces of 350 words with 50 words of overlap, split on word boundaries. The overlap exists so a sentence spanning a cut point still appears whole in one of the two pieces.

What an embedding is

In plain English

An embedding turns a piece of text into a long list of numbers — here, 768 of them — positioned so that texts with similar meaning end up with similar number-lists, even when they share no words.

"The review is late" and "periodic evaluation overdue" contain almost no overlapping vocabulary, but land close together. That closeness is measurable as an angle between the two lists, called cosine similarity, which runs from 0 (unrelated) to 1 (identical).

The embedding model is nomic-embed-text, running locally through Ollama — so document text never leaves the machine to be indexed. Chunks are embedded 32 at a time, and every vector is L2-normalised before storage so cosine comparisons behave consistently. Rate-limit responses get three bounded retries at 1, 2 and 4 seconds, respecting the provider's own retry hint when it sends one.

Indexing is all-or-nothing: a document either lands completely or not at all. There is no partial index, because a half-indexed document would silently answer questions from an incomplete evidence base — which looks identical to a working system right up until it matters.

Every chunk is embedded once at upload and stored in Qdrant, and chunks retain a link to their parent section. When you ask a question, your question is embedded the same way, and Qdrant returns the chunks whose number-lists sit nearest to it.

Why meaning-search alone isn't enough

Embeddings blur exact identifiers. A GxP corpus is full of tokens like URS-042, TC-2026-042 and ANNEX11-S4-DOC-001, and semantic similarity treats those as near-interchangeable noise. So a second, completely different search runs alongside it: BM25, a classic keyword-ranking algorithm that scores documents by term rarity and frequency. Its tokenizer deliberately keeps hyphenated identifiers intact, so URS-042 stays one searchable term rather than splitting into "urs" and "042".

Both searches run concurrently, each returning up to 20 candidates.

Fusing two incompatible rankings

Now there's a problem: cosine similarity runs 0–1, while BM25 scores are unbounded and depend on the corpus. Averaging them is meaningless. The solution is Reciprocal Rank Fusion, which throws the scores away entirely and uses only rank position:

fused_score(chunk) = Σ   1 / (k + rank)   summed across both result lists, k = 60

A chunk ranked 1st by both methods scores highest. A chunk both methods ranked reasonably beats one that a single method loved and the other ignored. No normalisation, no tuned weights.

Reranking, then the gate

The fused list goes to a language model in exactly one batched call — never one call per candidate, which at 20–40 candidates would take minutes — asking it to score each candidate's relevance from 0 to 1. The prompt states explicitly that the excerpts are untrusted data to be scored, not instructions to follow. Every returned score is coerced to a number, clamped to the 0–1 range, and discarded if it isn't numeric or names a chunk that wasn't in the candidate set.

Then the deterministic gate: only candidates scoring 0.35 or above survive, and at most 8 are kept. A candidate the reranker never scored is excluded rather than assumed to pass.

If reranking is unavailable

A fallback gate takes over, requiring a semantic score of at least 0.55 or a BM25 score of at least 1.0. That BM25 floor exists because of a real observation: an off-topic question about swallows still produced incidental keyword overlap scoring 0.28 on unrelated chunks, while a genuine match scored 3.22. Without a floor, that noise became a hedged answer instead of an honest refusal.

Two enrichments before answering

  • Parent context. Each surviving chunk's larger parent section is fetched — up to 2,000 characters — and attached for the answer-writing step. The chunk's own text is never modified, so the evidence panel always quotes exactly what was retrieved.
  • Graph relationships. Up to five real relationships involving the source documents are pulled from the evidence graph, so an answer can cite structural facts like "this document belongs to this system" that no text search would surface.

Finally, every piece of evidence carries a Python-composed explanation of why it was selected — naming the retrieval method and the actual scores. That sentence is assembled by code from real numbers, never written by a model, so the provenance shown to the user cannot itself be fabricated.

Every stage reports its own status to the interface as a live trace: understanding, searching, combining, reranking, evaluating, preparing. A stage that was skipped says so, and why.

Where the answer is actually written

One structural detail worth naming: the agent graph does not produce prose. It produces findings and retrieved evidence. The grounded, citing answer is composed afterwards, in the HTTP route, once the graph has returned — which keeps the fixed eleven-station topology untouched and keeps answer-writing clearly downstream of verification rather than tangled inside it.

When retrieval clears nothing above the gate, that path produces an explicit insufficient-evidence response that still names the documents it looked at, rather than a confident answer assembled from weak matches.

The rulebook: compliance as code

The ten compliance rules live in a language called Rego, running inside OPA as a separate service. They are not Python functions inside the app — they are a policy bundle the application calls out to, which means they can be tested, reviewed and versioned entirely on their own, and the application cannot quietly reinterpret them.

Each rule maps to a named clause of real regulation and emits a violation object naming the rule, the offending record and a severity.

#RuleCatchesSeverity

2ANNEX11-S12-ACC-001Access review overdue by more than 30 daysHIGH

4ANNEX11-S13-INC-001P1 incident open 7+ days with no root cause analysisHIGH
5ANNEX11-S4-TRC-001Requirement with no executed test evidenceHIGH

The rules share a corrected date helper. The obvious way to compute elapsed time in Rego returns a calendar breakdown, where the day component is a day-of-month remainder rather than a total — meaning a naive "more than 365 days" test could never be true. The bundle computes signed elapsed days from a raw nanosecond difference instead, so future-dated records yield negative values and correctly fail every overdue threshold.

The rules ship with their own test suite, run independently of the application.

09

The tamper-evident log

21 CFR Part 11 — the US electronic records regulation — requires audit trails that can be shown not to have been altered. AegisX implements this with a hash chain.

In plain English

A hash is a fingerprint of some data: a fixed-length string where changing even one character of the input produces a completely different output, and you can't work backwards from it.

In a hash chain, every entry's fingerprint is computed from its own content plus the previous entry's fingerprint. Altering entry #5 changes its fingerprint, which breaks entry #6's link, which breaks #7's, and so on to the end. You cannot quietly edit history; you can only break the chain visibly.

Each event covers fourteen fields — session, user, role, agent, action type, target system and record, input hash, output summary, evidence ids, rule ids, model id, prompt version, approval id — serialised into a canonical, sorted-key form so that the write side and the read side hash byte-identical input. The chain begins from a genesis value of 64 zeroes.

Two engineering details make it actually hold up:

  • A canonical field list, not "whatever was passed." If the write side hashed only the keys a caller supplied while verification hashed the full row, an event omitting one optional field would produce different bytes on each side, and every legitimate entry would report as tampered. Both sides drive off the same fixed fourteen-field list.
  • An exclusive table lock during writes. Two events written simultaneously could otherwise both read the same previous hash and fork the chain. The lock makes that impossible.

Verification walks every row in order, recomputes each hash, and reports either VERIFIED with a count or TAMPERED with the exact index and event id where the chain broke.

There is also a deliberate demonstration endpoint that modifies a chosen event so the break can be shown live. It is the only code path permitted to alter an audit row after insert, the act of calling it is itself audit-logged before it runs, and it correctly reports NO_SUCH_EVENT when pointed at an id that doesn't exist — rather than modifying nothing and reporting a misleading pass.

10

The evidence graph and blast radius

Compliance records are deeply interconnected: a requirement links to design elements, which link to test cases, which link to results; changes affect systems; incidents attach to systems. AegisX builds this into a directed graph — nodes joined by one-way arrows — using the NetworkX library.

Two rules govern what may become an edge, and they are strict:

  • Every edge traces to a real declared foreign key or an explicit junction-table row.
  • No edge is ever derived from two records merely sharing a system id, from text similarity, or from anything a model inferred.

Node ids are type-prefixed — DOCUMENT:DOC-2089EBE8D568, SYSTEM:GXP-MFG-DEMO-01 — so two tables that happen to use the same raw id can never collide into one node.

Blast radius

Pick any node and ask: if this changes, what else is affected? One graph traversal answers nine questions at once — direct dependencies, indirect dependencies, and affected requirements, tests, risks, changes, controls and systems.

It also computes two judgements, both from graph structure alone:

  • Potential GxP impact is HIGH if anything downstream is a GxP-relevant system or a patient-safety-relevant incident; MEDIUM if there is downstream impact at all; NONE if nothing is downstream.
  • Highest-impact downstream node is whichever affected node has the most descendants of its own, with ties broken by node type and then id — a total ordering, so the answer never depends on iteration order.

A model may be asked to explain a computed blast radius. It is never asked to compute one.

The model router and its safety nets

Where language models are used, requests go through a router that treats provider failure as normal rather than exceptional. Three providers sit in a cascade:

OrderProviderModelRole
1Ollama (local)qwen2.5:7b-instructRuns on the machine's own GPU. Handles orchestration, synthesis, compliance narration, knowledge, change, risk and reranking — no network, no quota, no cost.
2Groqopenai/gpt-oss-120bHosted, fast. Handles incident, access, high-volume work and remediation.
3OpenRouteropenrouter/autoGuaranteed last resort.

When a call fails, the router walks down this list, skipping any provider it has already tried, pausing one second between attempts so it doesn't hammer the next one. Every response reports the model id that actually produced it, so the interface can always name what answered.

Crucially, the router distinguishes failures that should move on from failures that shouldn't. A 401, 402 or 403 means this provider's account is broken — which says nothing about the others, so it cascades. A 400 or 422 means the request itself is malformed, which the next provider would reject identically, so it degrades immediately rather than wasting three round trips. A 200 response carrying an error payload — observed live from a proxy — is caught by the parser and treated as a real failure.

Four independent guards sit around this:

01

Circuit breaker

Gives the router memory. When six agents fan out in parallel and the first discovers a provider is rate-limited, the other five would each pay a full wasted round trip to learn the same thing. Instead the first failure trips the breaker open and the rest skip that provider entirely. After a cooldown — taken from the provider's own reported reset time when it sends one — a single probe call is allowed through to test recovery.

02

Rate limiter

Waits until a provider is back under its declared limits before sending, rather than reacting to a rejection afterwards. It tracks both requests per minute and tokens per minute — the latter matters because reasoning models silently consume hidden tokens, so request count alone badly understates real load.

03

Concurrency gate

Applies to the local model only. A hosted provider manages its own concurrency; a 7-billion-parameter model on a single consumer GPU does not. When the gate is full, the request cascades to the next provider instead of piling onto a saturated GPU.

04

Model keep-alive

Ollama unloads an idle model after five minutes, and reloading it costs around 15 seconds before a single token is generated — measured on this project's own hardware at 15.1s cold versus 0.8s warm. The router requests a 30-minute residency so the model stays in memory between questions. This is an infrastructure fix, not a timeout adjustment.

The router never raises an error to its caller. Exhausting every provider returns a clearly-marked degraded response carrying the full trail of what failed at each hop — and every caller is built to handle that.

What the user actually sees

Eleven pages in React, sharing a role selector that switches the active identity between IT System Manager, QA/Compliance and Auditor — which genuinely changes what the backend permits, not just what the interface shows.

  1. Command CentreReadiness dial and six health signals, computed live from backend state.
  2. Ask GxP CopilotThe chat. Live agent-topology canvas showing which stations are running, streamed answers, inspectable evidence.
  3. Evidence InvestigationThe Assurance Card for a single finding — claim, evidence, rule, deterministic check result, ALCOA+ breakdown.
  4. Audit ReadinessAggregate compliance posture across the system.
  5. Blast RadiusInteractive graph view. Pick a node, see everything downstream.
  6. KnowledgeDocument library and upload, with live ingestion progress through all six stages.
  7. Supplier IntelligenceSupplier qualification and reassessment status.
  8. ActionsThe approval queue. Pending proposals rendered from server-held data, awaiting a human decision.
  9. Assurance LabWhere verification behaviour can be exercised directly.
  10. Trust CentreAudit chain verification and the live tamper demonstration.
  11. Inspection SimulatorPractice inspection questions against the system.

One design rule runs through all of them: the frontend never invents a destination. The backend sends a kind plus an entity id — never a URL — and a single closed route map in the frontend is the only place those become navigable addresses. No address ever crosses the API boundary, which closes an entire class of redirect vulnerability by construction.
