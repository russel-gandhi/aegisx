<objective>
Answer "what else could be affected?" deterministically. Add a `blast_radius()`
traversal over the persisted evidence graph that answers every one of Bible Section
14.3's nine Graph Questions for a given node, expose it as a read-only endpoint, and
bring it to the SENT-3-03 Critical-review bar with unit, negative, edge-case and
integration coverage written directly from those nine questions.

**User story (MVP mode):** **As a** QA/Compliance user, **I want to** select the
change record that closed with unresolved actions and see exactly which requirements,
tests, documents and systems it touches downstream, **so that** I can scope the
impact without an AI guessing at relationships.

Purpose: this is the second half of the Phase 4 gate — "Blast Radius returns correct
downstream nodes for a seeded change record". The graph exists and is correct after
plan 04-02; this plan makes it answer questions. Bible Section 14.3 is explicit that
a model may explain impact but may never invent a relationship, so every number this
endpoint returns is produced by NetworkX reachability over real edges.

Output: `blast_radius()` and its two ranking helpers; the `BlastRadiusResponse`
model; `GET /api/systems/{system_id}/blast-radius`; `backend/tests/test_blast_radius.py`.
</objective>

<critical_findings>
Verified by direct file read during planning — do not re-derive, do not contradict:

1. **Bible Section 14.3's nine Graph Questions** (lines 1720-1732), verbatim, are the
   specification this plan implements and the source SENT-3-03's contract says the
   test cases must be written from: directly affected entities; indirectly affected
   entities; affected requirements; affected tests; affected risks; affected changes;
   affected controls; potential GxP impact; highest-impact downstream dependency.
   The response model has one field per question, plus `affected_systems`, because
   GRAPH-02's own wording names "affected tests/controls/systems".

2. **Bible Section 14.3 line 1750** states: "NetworkX reachability/traversal should
   calculate the affected subgraph. LLMs may explain or summarize impact, but should
   not invent graph relationships." No model call may appear in this plan's code.

3. **`nx.descendants(G, source)` raises `networkx.NetworkXError` when `source` is not
   a node of `G`** (NetworkX 3.6.1 documented behavior, cited in 04-RESEARCH.md
   Pattern 3). The route must catch that and return 404 — a change record with no
   derived edges, or a node id for a different system, is a valid and expected state.
   Returning 500 for it is a defect.

4. **The seeded graph after plan 04-02 has an exact, known shape** for
   `GXP-MFG-DEMO-01`: 14 nodes, 9 edges. `CHANGE:CR-2026-089` has four out-edges
   (`HAS_ACTION` to `CHANGE_ACTION:CA-2026-089-1`, and `AFFECTS` to
   `REQUIREMENT:URS-042`, `DOCUMENT:DOC-2026-OM-99`, `DESIGN_ELEMENT:DE-2026-DB-01`).
   `REQUIREMENT:URS-042` has one out-edge (`VERIFIED_BY` to `TEST_CASE:TC-2026-042`)
   and `DOCUMENT:DOC-2026-OM-99` has one (`GOVERNS` to `SYSTEM:GXP-MFG-DEMO-01`).
   The expected answer is therefore four direct, two indirect, six total downstream.

5. **`SYSTEM` is a graph sink.** Every relationship type that touches it
   (`GOVERNS`, `ASSOCIATED_WITH`, `AFFECTS` from an incident) points *into* the
   system node, and no edge leaves it. This is what keeps a blast radius bounded and
   is why `affected_systems` is a meaningful terminal answer rather than a gateway to
   everything.

6. **`affected_controls` is correctly empty for `CR-2026-089`.** Bible Section 14.3
   lists `ACCESS_REVIEW --CONTROLS--> ACCESS_RECORD`, but plan 04-02 established
   (critical finding 7 there) that `access_reviews` and `access_records` share no
   foreign key and D-03 rejects same-`system_id` association as a substitute. The
   controls bucket exists, is populated by `ACCESS_REVIEW`/`ACCESS_RECORD` node
   types, and correctly returns empty for this source node. Assert that empty result
   as a positive expectation, not as a gap.

7. **The domain graph today is acyclic**, so cycle, self-loop and disconnected-component
   coverage must be driven by hand-built `nx.DiGraph` fixtures in the unit section
   rather than by seeded data. That is legitimate: `blast_radius()` is a pure
   function over a graph object, and SENT-3-03's Critical-review bar requires the
   edge cases be proven, not assumed absent.

8. **`load_graph` already exists** (plan 04-01) and reconstructs the graph from the
   cache tables only. The blast-radius endpoint reads through it — it must not call
   `build_graph`, which would reintroduce rebuild-on-read (D-02).
</critical_findings>

Order: `SYSTEM`, `INCIDENT`, `RISK`, `REQUIREMENT`, `TEST_CASE`, `DOCUMENT`, `DESIGN_ELEMENT`, `CHANGE`, `CHANGE_ACTION`, `ACCESS_REVIEW`, `ACCESS_RECORD`, `SUPPLIER`, `SUPPLIER_ASSESSMENT`, `PERIODIC_EVALUATION`, `TEST_RESULT`.
