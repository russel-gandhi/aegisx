Note on the three "inverted" rows: the foreign key lives on the *child* table, so
the edge is drawn from the child row outward — declare those three as
`EdgeSpec(source_type=<child>, relation_type=..., target_type=<parent>, source_column=<fk column>)`
and then reverse the direction at draw time by a per-spec `parent_to_child: bool`
field on `EdgeSpec`, or equivalently declare them with the child as `source_type`
and add the edge as `parent -> child`. Choose one representation, state it in the
module docstring, and keep it uniform.

  <context>
    04-CONTEXT.md D-03 already locked the *existence* and rough shape of this table
    (`change_affects(change_id, entity_type, entity_id)`) and flagged it
    **one-way**: once `graph_edges` traversal and seeded demo data depend on the
    column shape, changing it needs a migration plus a reseed. The exact column
    names, types, constraints, and the related node-id convention were left to
    Claude's discretion — and those are precisely the one-way parts. This
    checkpoint confirms the door before it is walked through.

    The proposal on the table:
    - `change_affects(change_id VARCHAR(50) REFERENCES changes(id), entity_type VARCHAR(50), entity_id VARCHAR(50))`
      — one real foreign key on the `changes` side; `entity_id` is deliberately
      unconstrained because Postgres cannot express a foreign key spanning several
      target tables, and `entity_type` names which table `entity_id` resolves
      against, validated by a frozen Python allowlist rather than by the database.
      This mirrors `001_schema.sql`'s own stated style (no check constraints, no
      ON DELETE clauses) and `c1_verifier.py`'s allowlist-not-database-constraint
      precedent.
    - Graph node ids are type-prefixed (`REQUIREMENT:URS-042`), already implemented
      in plan 04-01. `change_affects` rows therefore resolve to a node id by
      joining `entity_type` and `entity_id`.
  </context>
  <options>
    <option id="as-proposed">
      <name>Ship the proposed shape (recommended)</name>
      <pros>Matches D-03's stated shape exactly; one real FK gives referential integrity where Postgres can express it; polymorphic side validated by a Python allowlist, consistent with the codebase's existing pattern; type-prefixed node ids make a graph_nodes primary-key collision structurally impossible.</pros>
      <cons>`entity_id` integrity is enforced in application code, not by the database — a bad row is dropped at build time with a warning rather than rejected at insert time.</cons>
