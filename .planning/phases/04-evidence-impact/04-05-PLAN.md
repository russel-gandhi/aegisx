<objective>
Close the loop between a finding and its impact. Wire the Blast Radius traversal
into the browser: clicking a node on the evidence graph shows what that entity is
and everything downstream of it, and every Assurance Card links straight to the
blast radius of its own evidence.

**User story (MVP mode):** **As a** QA/Compliance user, **I want to** click the
change record on the evidence graph — or follow a link from the finding I am already
investigating — and see the count of directly and indirectly affected entities and
the potential GxP impact, **so that** I can answer "what else could be affected?"
in the same place I answered "what is wrong?".

Purpose: this is SENT-3-04 plus the finding-integration constraint Bible Section
14.3 states explicitly — "Blast Radius should be integrated into the finding
investigation experience rather than presented as an unrelated standalone feature",
with the finding exposing Evidence, Verification and Blast Radius together. Plans
04-03 and 04-04 built the two halves; this plan connects them.

Output: `NodeDetailPanel` and `BlastRadiusPanel` components; node-click handling on
the evidence graph canvas; a deep-linkable node selection on `/blast-radius`; and a
per-evidence Blast Radius link on every Assurance Card.

Scope guard (D-05): this plan wires behavior, not polish. Node-type colour coding
beyond basic differentiation and the Bible Section 10.3 `animate-pulse` Trace Chain
highlight are explicitly deferred to Phase 6 and are not built here.
</objective>

<critical_findings>
Verified by direct file read during planning — do not re-derive, do not contradict:

1. **Bible Section 14.3's UI section (lines 1752-1777)** is the specification for
   this plan's two halves. It states the integration constraint verbatim, gives the
   finding's exposure tree as Finding → Evidence → Verification → Blast Radius, and
   gives the impact summary's own four-line shape: direct dependencies, indirect
   dependencies, affected controls, potential GxP impact — each a labelled value.

2. **D-05 defers all visual polish to Phase 6.** Node-type colour coding beyond
   basic differentiation and the `animate-pulse` Trace Chain highlight of Bible
   Section 10.3 are named in 04-CONTEXT.md's Deferred Ideas list. Phase 4's bar is
   "the graph is real, traversal is correct, and it is visible in the browser".
   Building the pulse animation here would be implementing a deferred idea.

3. **`@xyflow/react` v12 exposes node clicks via the `onNodeClick` prop** on
   `<ReactFlow>`, whose handler receives `(event, node)`. The node's `id` is the
   type-prefixed graph node id this plan's fetches key off. `EvidenceGraphCanvas`
   is currently a pure presentational component with no callback props (plan 04-01),
   so this plan adds one optional callback and keeps every other constraint.

4. **`react-router-dom` v7 is already a dependency** (`frontend/package.json`) and
   `AppShell` already wraps the routes in a router, so `useSearchParams` is
   available for the deep link with no new dependency and no routing change.

5. **Node ids contain a colon** (`CHANGE:CR-2026-089`), so both the blast-radius API
   call and the `?node=` deep link must apply `encodeURIComponent`. The backend
   takes `node_id` as a query parameter for exactly this reason (plan 04-04).

6. **An empty blast radius is HTTP 200, not 404** (plan 04-04's route contract). A
   node with no downstream edges — every `SYSTEM` node, and every isolated node —
   returns all-empty buckets with `potential_gxp_impact` `NONE`. The panel must
   render that as a real, meaningful result.

7. **The Assurance Card's `evidence_ids` are raw domain primary keys**
   (`PE-2024-01`), not graph node ids. The graph response's nodes carry both
   `node_id` and `entity_id` (plan 04-01's `GraphNode` model), so the link is built
   by matching a card's evidence id against a node's `entity_id` and using that
   node's `node_id`. No backend change is needed and none may be made in this plan.

8. **A card's evidence may have no node in the graph.** `periodic_evaluations` is a
   `NODE_SPECS` type, so `PE-2024-01` resolves; but a finding carrying the
   `NO-RECORD` marker has an empty `evidence_ids` list and therefore no link at all.
   Render the link only when a match exists.
</critical_findings>

**`frontend/src/components/NodeDetailPanel.tsx`**

Default-exported. Props: `{ node: EvidenceGraphNode | null }`. Renders the node's

select-a-node prompt when `node` is null.

**`frontend/src/components/BlastRadiusPanel.tsx`**

Default-exported. Props:
`{ result: BlastRadiusResponse | null; loading: boolean; error: string | null }`.
Renders Bible Section 14.3's four-line impact summary — direct dependencies,
indirect dependencies, affected controls, potential GxP impact — followed by the
per-question breakdown lists (requirements, tests, risks, changes, systems) and the
highest-impact downstream dependency. Every count is the `length` of a server-supplied
array; the component performs no fetch and no graph computation.

**`/blast-radius` deep link:** `?node=<url-encoded node id>` pre-selects that node
on mount.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Server response → rendered impact numbers | Every count shown must be the server's, never recomputed client-side |
| URL search parameter → API call | The `node` query parameter is user-controllable and is forwarded to the backend |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-09 | Tampering | Client-side recomputation of impact counts | high | mitigate | `BlastRadiusPanel` renders `length` of server-supplied arrays and nothing else; asserted by a grep-level acceptance criterion that no reachability term appears in the component and by a test that it issues no fetch. Bible Section 14.3 places traversal in the deterministic Python tier. |
| T-04-01 | Tampering | The `node` search parameter forwarded to the blast-radius endpoint | medium | mitigate | `encodeURIComponent` is applied on the way out; the backend never lets `node_id` reach SQL (plan 04-04, T-04-01), so a crafted value produces at worst a 404 the page renders as an error state. |
| T-04-10 | Information Disclosure | Node `properties` free-text values rendered in `NodeDetailPanel` | low | mitigate | React escapes interpolated text by default and no HTML-injection API is used; the values are synthetic demo data behind the prototype banner, and the property columns were allowlisted server-side in plan 04-02. |
