<objective>
Make Phase 3's verified finding *visible*. A backend route assembles the
already-computed `AgentFinding` and C1 verification pair for a system, and a
reusable `AssuranceCard` React component renders CLAIM / EVIDENCE / RULE /
DETERMINISTIC CHECK / CONFIDENCE from that server-trusted payload and nothing else.

**User story (MVP mode):** **As a** QA/Compliance user, **I want to** see each AI
compliance claim next to the exact database records, the exact regulatory rule, the
exact deterministic check, and the confidence the system independently assigned it,
**so that** I can tell whether to trust the claim without trusting the model.

Purpose: this is the product's core thesis made legible. Phase 3 proved C1 grades
claims correctly against real Postgres and real OPA; until this plan, nobody can see
it. Per D-04 the card is built as a reusable component behind its own investigation
route now, so Phase 6 drops the same component into the Copilot chat thread rather
than building a second card.

Output: `GET /api/systems/{system_id}/assurance-cards`; the `AssuranceCard` and
`DeterministicCheck` Pydantic models; `AssuranceCard.tsx`; the `/findings` frontend
route; backend and frontend tests.

This plan is mechanically independent of the evidence graph — it shares only the
discipline that no field may be synthesized anywhere but the server.
</objective>

<critical_findings>
Verified by direct file read during planning — do not re-derive, do not contradict:

1. **Every field the card needs already exists and is already computed.**
   `backend/app/agents/c1_verifier.py`'s `verify_finding(pool, finding)` returns
   exactly `{"confidence", "db_record_found", "opa_corroborated", "opa_rule_ids", "evidence_ids"}`,
   and `backend/app/agents/a2_compliance.py`'s `build_finding(...)` returns
   `{"finding_id", "claim", "regulatory_citations", "confidence_score", "evidence_ids", "alcoa_score", "model_attribution"}`.
   `backend/README.md` line 224 states plainly that `verification_results` "is the
   shape Phase 4's Assurance Card UI reads its data from". **No new verification
   logic is written in this plan** (D-04, and CLAUDE.md Rule 7).

2. **`c1_verifier.py` and `a2_compliance.py` are read-only in this plan.**
   04-CONTEXT.md's code-context section states Phase 4 consumes C1 as read-only
   input and does not modify it. Import `A2_CHECKS`, `narrate_gap`, `build_finding`
   from `a2_compliance` and `verify_finding` from `c1_verifier`; edit neither file.
   Both are Critical-review Phase 3 deliverables (CLAUDE.md Rule 10 — no two agents
   editing the same critical file).

3. **The "DETERMINISTIC CHECK" field is not in the finding dict today.** A2's check
   functions return `{"check", "rule_id", "passed", "record"}`, but
   `build_finding` drops the `check` name — the finding only keeps `finding_id`,
   which encodes the rule id and record id. The route must therefore assemble the
   card from the check result *and* the finding *and* the verification result. This
   is why the route calls `A2_CHECKS` directly rather than invoking the compiled
   LangGraph, and it needs no change to either Phase 3 module.

4. **`narrate_gap` degrades cleanly with no API key.** `backend/app/llm_router.py`'s
   `_resolve_api_key` returns `None` when no key is set and `call_llm` returns a
   degraded `LLMResponse` **without making a network call**; `narrate_gap` then
   returns a deterministic template sentence and the literal `deterministic-fallback`
   as the model attribution. The route therefore works offline, with no key, in
   well under a second — but the `claim` text will be the template, not model prose.
   Surface `model_attribution` on the card so the operator can see which it was.

5. **A2 emits findings only for checks that FAIL.** `run_a2` skips passing checks.
   Against `GXP-MFG-DEMO-01` the seeded state makes `verify_urs_approved` pass (the
   `DOC-2026-URS-01` fixture is `APPROVED`), while `verify_periodic_eval_current`
   and `verify_test_traceability` both fail. Expect **two** cards for that system.
   Per `backend/README.md`'s C1 coverage section, the periodic-evaluation finding
   grades `MEDIUM` (real record plus OPA corroboration via rule 7) and the
   traceability finding grades `MEDIUM` (rule 5 fires on the `DRAFT` `TC-2026-042`).
   Against `BUS-IT-DEMO-02`, `verify_periodic_eval_current` fails with a `None`
   record, `build_finding` emits the `NO-RECORD` marker finding with empty
   `evidence_ids`, and C1 grades it `INSUFFICIENT_EVIDENCE` — the discrimination
   control this plan must render, not hide.

6. **`confidence_score` on the finding itself is the literal `UNVERIFIED`.**
   `backend/README.md`'s "AgentFinding conventions" table fixes this: only C1
   assigns a real grade, and it does so into `verification_results`, not back onto
   the finding. The card's CONFIDENCE field must therefore read from the
   verification result, never from `finding["confidence_score"]`. Reading the wrong
   one is the single most likely defect in this plan.

7. **`frontend/src/routes.tsx` will have nine entries** once plan 04-01 merges, and
   `frontend/src/__tests__/routes.test.tsx` will assert `toHaveLength(9)` with a
   nine-key `expectedHeadings` map. This plan takes both to ten. Re-read both files
   at execution time rather than assuming the count.

8. **`frontend/src/lib/api.ts` already exists** after plan 04-01, exporting
   `apiGet<T>`, `resolveApiBase`, and `fetchEvidenceGraph`. Extend it; do not create
   a second HTTP helper module.
</critical_findings>
