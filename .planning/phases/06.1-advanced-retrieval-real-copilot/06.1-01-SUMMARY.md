## Decisions Made

- **README deviation numbering split from the code/migration's own locked number.** The migration file and `embeddings.py` module docstrings lock the literal text "Deviation 13"/"Deviation 14" (per the plan's exact required wording). `backend/README.md`'s own heading numbering is a separately-incrementing sequence (established precedent: the existing "Deviation 10" heading is numbered by "highest existing heading + 1", not by the code docstring's own number). The new README heading is "Deviation 11", with an explicit one-sentence note in the entry itself explaining the two numbers name the same change.
- **Qdrant-unavailable guard added ahead of any write in `routes/documents.py`.** Not explicitly itemized in the plan's guard list, but `get_qdrant_client()` already mirrors `acquire_pool_or_none()`'s degrade-don't-raise contract, and without an explicit check the `documents` row would be written before an unreachable-Qdrant failure surfaced deep inside `index_document`'s upsert call -- a partial-state bug the Postgres guard already prevents for its own failure mode. Checked immediately after the Postgres guards, before `document_id` generation or any INSERT.
- **`chunk_blocks()`'s metadata does not carry `source_filename`.** The plan's own artifact section locks `chunk_blocks(blocks: List[ParsedBlock]) -> List[Chunk]` with no filename parameter, so the filename cannot originate inside that pure function. `routes/documents.py` -- the one caller that actually has the client filename -- sets `chunk.metadata["source_filename"]` itself, after chunking and before calling `index_document`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `call_embedding()`'s `response.json()` call was unguarded against a malformed/non-JSON response body**
- **Found during:** Task 1, while writing `test_retrieval_ingest.py`'s integration test against the mocked batch endpoint's own failure path
- **Issue:** `response.json()` sat inside the same `try` block as the HTTP call, but the `except` clauses only caught `httpx.TimeoutException`/`HTTPStatusError`/`RequestError` -- a genuinely malformed or empty response body raised `json.JSONDecodeError` uncaught, violating the module's own documented "never raises to its caller" contract (the same contract `_call_batch_group`'s sibling code path already honored via a `ValueError` catch).
- **Fix:** Added an explicit `except ValueError:` clause (catches `json.JSONDecodeError`, a `ValueError` subclass) that degrades with `failure_reason="invalid_json_response:{entry_key}"`, mirroring the batch path's existing guard.
- **Files modified:** `backend/app/retrieval/embeddings.py`
- **Verification:** Reproduced live (a sandboxed-network response with an empty body surfaced exactly this uncaught exception before the fix); `test_retrieval_ingest.py`'s integration suite passes cleanly after the fix.
- **Committed in:** `84682ed` (part of Task 1's commit)

**2. [Rule 3 - Blocking issue] Two worktree-local setup gaps blocked any execution: no `.env` and no `backend/.venv`**
- **Found during:** start of Task 1, before the first `pip install`
- **Issue:** `.env` and `backend/.venv` are both gitignored, so a fresh worktree (this one branched from an earlier commit and then fast-forwarded to pick up the plan files) had neither. Without `.env`, `docker compose exec`/`infra/apply-migrations.sh` failed with "POSTGRES_PASSWORD is unset" (compose file interpolation error) even though the actual Postgres/Qdrant/OPA containers were already running and healthy. Without `.venv`, no Python dependency existed to install into.
- **Fix:** `cp .env.example .env` (placeholder values only -- no secret was read, generated, or invented; `.env.example`'s own contents were never displayed, only copied) and `python -m venv backend/.venv` followed by the pinned `pip install -r backend/requirements.txt`, per `backend/README.md`'s own documented project-local-venv setup instructions.
- **Files modified:** none tracked (`.env`, `backend/.venv/` are both gitignored, confirmed via `git status --short` showing neither)
- **Verification:** `docker compose ps` succeeded afterward; `infra/apply-migrations.sh` applied cleanly; `asyncpg` connected to live Postgres.
- **Committed in:** n/a (no tracked files changed by this fix)

## Issues Encountered

- **respx's `assert_all_mocked=False` silently short-circuited ALL requests (including the intended-to-be-mocked one) to an empty 200 response in this sandbox**, rather than passing unmatched requests through to the real network as documented. Confirmed by direct reproduction (`route.called == False` yet a fake `200 b''` response was returned). Worked around by using `respx.route(url__startswith=QDRANT_URL).pass_through()` as an explicit registered route instead, which behaves correctly under the default `assert_all_mocked=True`. Recorded as a new test pattern above for the remaining six plans in this phase to reuse.
- **The plan's literal `python -c "from app.main import app; print([r.path for r in app.routes if 'documents' in r.path])"` verify command fails** on the pinned `fastapi==0.141.1`: this FastAPI version represents included routers as `_IncludedRouter` wrapper objects in `app.routes` (no `.path` attribute), not flattened `APIRoute` objects -- a FastAPI internals change unrelated to this plan's own code. Verified the route is genuinely registered and functional via `app.routes[i].original_router.routes` traversal and, more importantly, a live `TestClient` request (422 for missing required fields, not 404) and a real running-server smoke test (see below). This same internals change affects the identical verify-command pattern for every prior phase's router registration, not just this plan's.
