<objective>
Complete D-04's format scope: PDF, DOCX and CSV join Markdown/plain text as real
ingestion paths, each producing the structure the retrieval layer already expects —
PDFs carry page numbers, DOCX carries heading-derived sections, CSV gets its own
row/column path rather than being pushed through the prose chunker. Then close the two
gaps that make ingestion feel real rather than demo-shaped: a Knowledge list endpoint,
and an automatic evidence-graph rebuild so a just-uploaded document is not invisible
to graph expansion.

Purpose: `06.1-RESEARCH.md` Pitfall 2 is the sharpest failure mode here — `load_graph`
reads only the `graph_nodes`/`graph_edges` cache tables, so without a rebuild trigger a
freshly uploaded document exists in `documents` but never appears in Blast Radius or in
graph-expanded Copilot answers. That is exactly the kind of quietly-wrong demo the
deterministic-first architecture exists to prevent.
Output: three new parsers, a sniffing dispatcher, `GET /api/documents`, and the
post-upload rebuild side effect.
</objective>

|-----------|----------|-----------|----------|-------------|-----------------|
| T-06.1-20 | Denial of Service | zip-bomb / high-page-count PDF or DOCX | high | mitigate | `MAX_UPLOAD_BYTES = 10 MiB` (plan 06.1-01) checked before parse, plus `MAX_PDF_PAGES = 500` and `MAX_CSV_ROWS = 5000` bounding per-format work; `MAX_CHUNKS_PER_DOCUMENT = 500` bounds the downstream embedding fan-out |
| T-06.1-21 | Tampering | file-type confusion (binary payload behind a text extension, or vice versa) | high | mitigate | `detect_format` requires extension AND content agreement — `%PDF-` / `PK\x03\x04` magic bytes for binaries, a strict UTF-8 decode for text/CSV; a mismatch returns `None` → 415 before any parser is invoked |
| T-06.1-22 | Tampering | parser crash treated as a successful ingest | medium | mitigate | Both binary parsers are wrapped in a broad-exception guard returning `[]`, which the route maps to `status="FAILED"`, `failed_stage="parsing"` with zero chunk rows written — never a silent partial success |
| T-06.1-23 | Tampering | SQL injection via the `system_id` list filter | medium | mitigate | `$1::varchar IS NULL OR d.system_id = $1` — one parameterised statement; no f-string SQL anywhere in the module |
| T-06.1-24 | Elevation of Privilege | unauthenticated read of the document inventory | medium | mitigate | `Depends(require_identity)` on `GET /api/documents`, matching the upload route rather than following the deliberately-ungated Phase 4 read-route precedent — a document inventory is closer to a write-route's sensitivity than to a public health check |
| T-06.1-25 | Repudiation | graph rebuild failure silently corrupting evidence provenance | medium | mitigate | The rebuild failure is logged with `exc_info=True` and its consequence (stale graph expansion until the next rebuild) is stated in the route docstring; the deterministic `POST /api/systems/{system_id}/evidence-graph/rebuild` route remains available as the explicit recovery path |
</threat_model>
