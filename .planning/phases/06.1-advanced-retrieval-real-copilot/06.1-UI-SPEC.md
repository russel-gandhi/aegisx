# Phase 06.1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** Covers the three new/extended frontend surfaces this phase's success criterion 5 and RAG-07 require: a **Knowledge** page (`frontend/src/pages/Knowledge.tsx`, new — RAG-01, D-10), an **Investigation Trace** panel embedded in the Copilot chat (`frontend/src/components/InvestigationTrace.tsx`, new — RAG-03/04/06, D-10), and an **Evidence View** that extends `AssuranceCard.tsx`'s existing visual pattern for retrieval-sourced evidence (`frontend/src/components/EvidenceView.tsx`, new — RAG-05/07, D-11). It also covers the copy/interaction changes to the existing `Copilot.tsx` chat shell required by D-07 (relaxing the hero-query-only regex gate). It does **not** re-specify `AssuranceCard.tsx`, `ChatMessage.tsx`, or `AgentTopologyCanvas.tsx`, which are reused unmodified per D-11/D-07 — see `06-UI-SPEC.md` for their original contract. It does not cover Blast Radius (Phase 06.1.1's scope) or any Trust Centre/Supplier work (out of scope per D-12).

**shadcn gate — decision:** No `components.json` exists in this repo (confirmed again this session), and the stack is React + Vite. **Declined again**, continuing the precedent set in `05-UI-SPEC.md` and `06-UI-SPEC.md`: six phases (2 through 6) have shipped a consistent, hand-built Tailwind v4 dark design system with no component library, and `06.1-CONTEXT.md`'s own locked decisions (D-11: "extends the existing `AssuranceCard` provenance pattern... reusing that visual language rather than inventing a new one"; D-12: "no new top-level nav items... do not add decorative analytics") reinforce continuing the existing hand-built system rather than introducing one now, mid-loop, for three net-new components. `06.1-RESEARCH.md` proposes zero new frontend npm packages (its entire Standard Stack is backend/Python) — there is no dependency pressure toward shadcn this phase either. Icon library stays declined (text-only labels/badges, unchanged since Phase 2).

## Spacing Scale

Declared values (multiples of 4), identical to `05-UI-SPEC.md`/`06-UI-SPEC.md` — no new scale introduced:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Stage-glyph-to-label gap, badge micro-padding (retrieval-method badges, evidence-type badges) |
| sm | 8px | Compact element spacing (processing-checklist row gaps, evidence-item internal gaps) |
| md | 16px | Default element spacing (`mt-4`, card `p-4`) — Knowledge source-list row padding, Investigation Trace panel internal rhythm |
| lg | 24px | Section/page padding (`<main className="p-6">`, unchanged) — Knowledge page section gaps (drop zone → processing list → source list) |
| xl | 32px | Reserved — not used this phase (no new full-page section breaks beyond what `lg` covers) |
| 2xl | 48px | Reserved — not used this phase |
| 3xl | 64px | Reserved — not used this phase |

Exceptions:
- Drop zone (`Knowledge.tsx` §7.1): fixed `min-height: 160px` (component dimension, not a spacing token) — large enough to read as an obvious drop target without becoming an oversized empty area (`UI_SPEC.md` §4.2 explicitly warns against "huge empty dashboard areas").
- Evidence View / Investigation Trace panel max-width: `max-w-2xl`, matching the existing chat-bubble max-width convention in `ChatMessage.tsx` — these panels render *inside* an assistant chat bubble, so they inherit its width constraint rather than defining a new one.

Identical to `05-UI-SPEC.md`/`06-UI-SPEC.md` — reused, not re-derived:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|

## Color

Identical palette to `05-UI-SPEC.md`/`06-UI-SPEC.md` — **no new hues introduced this phase**, only new semantic assignments layered onto the existing four hue families. This is a deliberate reinforcement of `UI_SPEC.md` §4.2/§23's explicit warnings against "generic purple/blue AI aesthetics" and "using color merely for decoration" — retrieval-method and evidence-type distinctions in this phase are carried by **text labels**, not by introducing a fifth hue.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `slate-950` (#020617) | Page background (unchanged) |
| Secondary (30%) | `slate-900` (#0f172a) surfaces, `slate-800` (#1e293b) borders | Knowledge source-list rows, drop zone container, Investigation Trace panel, Evidence View panel |
| Accent (10%) | `emerald-600`/`emerald-700` (#059669 / #047857) | Reserved for exactly: the "Browse files" upload button; a completed (`✓`) ingestion/investigation stage glyph; the "High evidence support" badge (reuses `AssuranceCard`'s existing `HIGH` confidence hue verbatim, per D-11) |
| Destructive | `red-700` (#b91c1c) | Reserved for exactly: upload-rejected errors (unsupported type / too large), ingestion-failure errors, the "Insufficient evidence" badge (reuses `AssuranceCard`'s existing `INSUFFICIENT_EVIDENCE` hue verbatim) |

Accent reserved for **only** the three elements listed above — never applied to hover states, nav-active state, or decoratively to badges that aren't communicating a positive/complete/high-confidence state.

New semantic mappings this phase introduces, reusing existing hues only (no new hex values):

| Signal | Hue | Rationale |
|--------|-----|-----------|
| Ingestion/Investigation stage: complete (`✓`) | `emerald-600` glyph, `text-slate-100` label | Matches the existing "Complete"/accent success semantics |
| Ingestion/Investigation stage: in progress (`◌`) | `amber-600` glyph, `text-slate-200` label | Matches `AssuranceCard`'s existing `MEDIUM` hue and Phase 6's "Running" topology-node hue — established in-progress semantics |
| Ingestion/Investigation stage: not yet started (`-`) | `text-slate-500` glyph and label | Neutral, dimmed — matches Phase 6's `opacity-40` "not exercised" convention in spirit (a static, not-yet-real state, never styled as an error) |
| Evidence-support badge: High | `emerald-700`/`emerald-950/40` | Reuses `AssuranceCard`'s `HIGH` styling verbatim (`border-emerald-700 bg-emerald-950/40` / `bg-emerald-700 text-emerald-50`) |
| Evidence-support badge: Moderate | `amber-700`/`amber-950/40` | Reuses `AssuranceCard`'s `MEDIUM` styling verbatim |
| Evidence-support badge: Limited | `orange-700`/`orange-950/40` | Reuses `AssuranceCard`'s `LOW` styling verbatim |
| Evidence-support badge: Insufficient evidence | `red-700`/`red-950/40` | Reuses `AssuranceCard`'s `INSUFFICIENT_EVIDENCE` styling verbatim |
| Retrieval-method badge (Semantic / Keyword / Hybrid) | `slate-800` bg, `slate-300` text, no accent | Deliberately neutral — this is a provenance fact, not a quality signal; giving it its own accent color would wrongly imply "hybrid is better than semantic," which is not a claim this UI should make |
| Evidence-type label (Document evidence / Graph relationship / AI-synthesized answer) | `slate-800` bg, `slate-300` text, no accent | Same rationale — `UI_SPEC.md` §11/§18 requires the user be able to *distinguish* these categories, not rank them by color; text label carries the distinction |

## Animation Contract

*(Non-template section — continues `06-UI-SPEC.md`'s CSS-only precedent; no new runtime dependency introduced.)*

| Surface | Animation | Implementation | Constraint |
|---------|-----------|-----------------|-----------|
| Ingestion stage glyph, on stage completion | Color transition (`-` → `◌` → `✓`) | `transition-colors duration-300`, same class/duration as Phase 6's topology-node status transition — direct reuse | Only animates on a real status change (guard with previous value in state), never a decorative loop |
| Knowledge source-list row, on mount | Subtle fade-in + 4px slide-up | `transition-all duration-300 ease-out`, same pattern as Phase 6's mini-cards | ≤300ms; row is clickable/readable immediately |
| Investigation Trace panel, stage-by-stage reveal | Fade-in per stage row | `transition-opacity duration-200`, staggered ~40ms per row (same inline-`style` stagger technique as Phase 6's mini-cards, no stagger library) | Reveal happens once, on response arrival — never re-plays on re-render; must not delay the grounded answer text itself from being readable |
| Evidence View, evidence-item expand/collapse ("Show N more") | Height/opacity transition | `transition-all duration-200` | Content must remain in the DOM and keyboard-reachable when collapsed (accessibility — `UI_SPEC.md` §27), not `display: none`d abruptly |

Explicit non-goals (unchanged from `06-UI-SPEC.md`): no floating/particle effects, no gradient backgrounds, no spring-physics easing, no skeleton-shimmer components. No fabricated per-stage live progress animation this phase — see Interaction Notes below for why.

## Interaction Notes (non-template, load-bearing for planner/executor)

**Investigation Trace stage mapping (resolves the real-backend-operations requirement, D-10):**

| # | UI stage label | Real backend operation | Notes |
|---|-----------------|--------------------------|-------|
| 1 | Understanding question | A0 Orchestrator intent classification (`run_a0`, unchanged, already real) | |
| 2 | Searching knowledge | A1's dense (Qdrant `query_points`) + lexical (`rank_bm25.BM25Okapi`) candidate retrieval, run for this query | Rendered as one combined stage — the UI does not claim to show dense/lexical as separately timed sub-stages this phase |
| 3 | Combining semantic and keyword evidence | Reciprocal Rank Fusion of the two candidate lists (deterministic, no LLM) | |
| 4 | Reranking candidates | The single batched `call_llm(task="rerank", json_output=True)` call (Pitfall 3/4 in RESEARCH — must stay one call, never N) | |
| 5 | Evaluating evidence | The deterministic relevance-threshold gate (D-08/D-09) — decides per-item pass/fail against the fixed cutoff, and decides whether the overall answer is "insufficient evidence" | If this stage yields zero passing items, the trace still renders as complete (the check genuinely ran), and the Evidence View renders the insufficient-evidence Copywriting Contract row — this is a real negative result, not a failure |
| 6 | Preparing assessment | The new answer-synthesis call (`task="synthesis"`, in the HTTP route per RESEARCH's Pitfall 1 finding) | Parent-context expansion and graph expansion (`DOCUMENT` node reuse) happen inside stage 5/6's window and are not broken into their own top-level trace rows this phase — their output (section/page provenance, graph-derived relationships) surfaces in the Evidence View instead, not as separate trace stages |

**Why no live per-stage streaming this phase:** `06.1-RESEARCH.md`'s architecture places `compiled_graph.ainvoke()` as a single awaited call, with answer synthesis running afterward in the HTTP route — there is no per-stage push channel analogous to the hero-query SSE path for this new free-text path. Rendering a stage-by-stage progress animation that isn't backed by real per-stage server events would violate `UI_SPEC.md` §7.2/§9's explicit "must correspond to actual backend operations... never animate fake progress independently of the backend" rule. The contract here is therefore: show a single honest "Investigating…" state while in flight, then reveal the full stage sequence, each marked complete/skipped from the real response's own stage metadata, once the response arrives. If a later plan wires a true per-stage SSE channel for this path, upgrading the loading state to live per-stage transitions is a valid enhancement that does not require a new UI-SPEC — it is additive to, not a contradiction of, this contract's populated-state row.

**Evidence-type distinction (resolves `UI_SPEC.md` §11/§18's "distinguish source evidence / system-derived relationship / model interpretation" requirement):** Every evidence item in the Evidence View carries an explicit type label, not just a citation:
- **Document evidence** — a retrieved chunk, cited with source document + section/page (Section 15.7 provenance fields).
- **Graph relationship** — a `DOCUMENT`-node graph-expansion result (deterministic, from `evidence_graph.py`, per RESEARCH Pattern 4) — labeled distinctly from a document citation since it's a derived relationship, not quoted text.
- **AI-synthesized answer** — the grounded-answer paragraph itself is visually the *conclusion*, always rendered above/separate from the EVIDENCE list (mirrors `UI_SPEC.md` §11's example: ASSESSMENT text first, then WHY, then EVIDENCE) — never interleaved with evidence items in a way that could be mistaken for a cited fact.

**Routing (resolves RESEARCH Open Question 2):** Knowledge is added as **one new flat top-level route** (`/knowledge`), matching `NavBar.tsx`/`routes.tsx`'s existing flat-list pattern verbatim — no grouped/dropdown nav rebuild this phase. This directly follows the researcher's own recommendation and keeps D-12's "no new top-level nav items beyond what's needed" satisfied literally (one addition, for one genuinely new capability).

**System selection on upload (resolves RESEARCH Open Question 1 as a UI contract):** The Knowledge upload control requires a system selection before "Browse files" is enabled — a `<select>` reusing `BlastRadius.tsx`'s existing markup/classes (`rounded border border-slate-700 bg-slate-900 px-2 py-1 text-sm text-slate-100`) with options `GXP-MFG-DEMO-01` / `BUS-IT-DEMO-02` (no "All Systems" option here, unlike Command Centre's selector — a document must belong to exactly one system for graph expansion to work, per RESEARCH Pitfall 3).

**Non-hero-query answer path (resolves D-07's frontend-visible change):** `Copilot.tsx`'s `matchHeroQuery()` gate stays as a fast-path check only (per D-07's own "can remain as an optimization" wording) — any input that does NOT match it now goes to the real graph-backed route instead of `UNRECOGNIZED_SHAPE_COPY`. The assistant's chat bubble for this path renders, in order: (1) the grounded-answer paragraph, (2) an "How AegisX searched" toggle opening the Investigation Trace panel, (3) the Evidence View evidence-item list — or, if D-09's threshold gate found nothing, the insufficient-evidence Copywriting Contract row in place of all three. Injection-blocked responses (`detect_injection()` still running first via C2, unchanged) keep their existing destructive-styled bubble treatment from `06-UI-SPEC.md`, unmodified.
