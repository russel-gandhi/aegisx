## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `hybrid_reranked`'s retrieved list included unconditional graph-relationship evidence items, dragging precision@5 to 0.2 against a lexical_only/dense_only baseline of ~0.18-0.2**
- **Found during:** Task 2, first live run of the full evaluation
- **Issue:** `expand_graph_evidence` appends graph-relationship items to `hybrid_retrieve`'s evidence list unconditionally, after -- not subject to -- the fusion/reranking gate this evaluation measures. Counting their `chunk_id` (a graph node id, never a real `document_chunks` row) as a "retrieved" candidate meant no `relevant_markers` substring check could ever match it, penalising `hybrid_reranked` against `dense_only`/`lexical_only` (which never see graph evidence) for a category of evidence this plan was never measuring.
- **Fix:** `_hybrid_reranked_ids` filters out `evidence_type == "graph_relationship"` items before comparison, with the rationale documented in the function's own docstring.
- **Verification:** `hybrid_reranked` precision@5/recall@5/MRR moved to 1.0/1.0/1.0, correctly `>=` both single-method configurations.
- **Committed in:** `c19e847` (Task 2 commit)

**2. [Rule 1 - Bug] The mock rerank oracle's `LLMResponse` construction was missing the required `provider` field, silently degrading every reranking call to the deterministic fallback gate**
- **Found during:** Task 2, debugging the same low-precision symptom above
- **Issue:** `LLMResponse` requires `provider: str`; the oracle omitted it, so every call raised a pydantic `ValidationError`, caught by `rerank_batch`'s own broad exception guard and silently degraded to the Task 1 dense-score/BM25-presence fallback gate instead of the intended oracle-scored real reranking path.
- **Fix:** Added `provider="google"` to the oracle's `LLMResponse(...)` construction.
- **Verification:** Confirmed via a standalone debug script showing real oracle scores (0.9/0.05) reaching the gate instead of the fallback; `hybrid_reranked` precision/recall/MRR jumped to 1.0/1.0/1.0 from the fallback gate's ~0.2/1.0/varied.
- **Committed in:** `c19e847` (Task 2 commit)

**3. [Rule 1 - Bug] Session-scoped `eval_corpus`/`live_eval_report` fixtures left the evidence graph polluted with 3 extra DOCUMENT nodes for the rest of the pytest session, breaking `test_routes_evidence_graph.py`'s fixed node/edge-count assertions**
- **Found during:** first full-backend-suite run after Task 2's initial implementation
- **Issue:** Each eval-corpus upload triggers 06.1-04's post-upload evidence-graph auto-rebuild, which REPLACES (not appends to) `GXP-MFG-DEMO-01`'s cached `graph_nodes`/`graph_edges` with a snapshot including the 3 eval documents. Deleting the documents/chunks in teardown did not revert that cache, so any test file running afterward in the same session (`test_routes_evidence_graph.py`) saw 17 nodes/11 edges instead of the expected 14/9.
- **Fix:** Changed both fixtures from `scope="session"` to `scope="module"` (confines the pollution window to this file's own tests) and added an explicit `build_graph`/`persist_graph` rebuild in `eval_corpus`'s teardown, after deleting the eval documents' rows, restoring the graph to its pre-fixture state.
- **Verification:** `pytest tests/test_retrieval_eval.py tests/test_routes_evidence_graph.py -q` green (39 passed); full backend suite subsequently green (548 passed) across two separate runs.
- **Committed in:** `c19e847` (Task 2 commit)

**4. [Rule 3 - Blocking issue] Fresh worktree had no Python virtual environment**
- **Found during:** start of execution, before writing any fixture file
- **Issue:** `backend/.venv` did not exist in this worktree; the pinned `numpy` requires Python >=3.11.
- **Fix:** Created `.venv` against the system's Python 3.12 interpreter (`py -3.12 -m venv .venv`), then `pip install -r requirements.txt` cleanly.
- **Verification:** `pip install` completed with zero errors; the full backend suite ran green immediately after.
- **Committed in:** n/a (`.venv` is not tracked)

## Issues Encountered

- **A naive arbitrary-formula embedding mock (the pattern already used in `test_routes_documents.py`) could not support this plan's discriminating-power requirement.** Dense search "winning" a true paraphrase case requires the mock to encode genuine (even if simplified) semantic similarity between differently-worded texts; an arbitrary formula produces essentially random vectors with respect to meaning. Resolved by designing a deterministic "concept-tag" oracle keyed on each corpus chunk's own distinctive record-id marker and each labelled query's own exact text -- documented at length in `test_retrieval_eval.py` and cross-referenced from `backend/README.md`, including the explicit limitation that this proves pipeline wiring, not live embedding-model quality.
- **The plan's Task 2 `<read_first>` pointer to `test_evidence_graph.py`'s "existing live-service guard convention" does not literally exist there** -- that file (and every other integration test in this phase) asserts `client is not None` and fails loud rather than skipping. This plan's `<behavior>` explicitly requires a clean `skipped` (not `failed`) outcome, so a `pytest.skip`-based guard was built fresh (`_live_services_available`/`_skip_unless_live_services` pattern) rather than reused from a precedent that turned out not to exist in the cited form. Verified live by stopping the Qdrant container.
- **A ~56-minute full-suite run showed 4 unexpected failures in `test_routes_findings.py`** (a file untouched by this plan) with `httpx.ConnectError`. Traced to transient Docker connectivity during an unusually long run (likely related to the Qdrant container stop/restart cycle performed minutes earlier to verify the skip-guard behavior). Re-verified: `test_routes_findings.py` alone passes 18/18 with all containers healthy, and two other full-suite runs bracketing this one (immediately after each task commit) both showed 548/548 passing.
