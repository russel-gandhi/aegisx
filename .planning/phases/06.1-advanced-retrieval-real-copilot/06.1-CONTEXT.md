# Phase 06.1: Advanced Retrieval & Real Copilot - Context

<domain>
## Phase Boundary

The AegisX Copilot currently only answers one literal hero-query shape ("Is {known system id} audit ready?") via a client-side regex match; every other input hits a stub route (`POST /api/copilot/query`) that only runs `detect_injection()` and always returns `supported: false`. The full LangGraph orchestrator (`C2 → A0 → [A1-A6] → C1 → A7 → C3`, `app/graph/state.py::compiled_graph`) is fully built and tested but never invoked by any live HTTP route. A1's Qdrant retrieval is a stub (validates `system_id` exists, no vector search). Qdrant itself is running (healthy, empty) with zero collections and zero client code anywhere in the backend.

This phase builds the real evidence loop end to end: **document upload → parsing → structure-aware chunking → hybrid (dense+lexical) retrieval → cross-encoder reranking → evidence filtering → grounded LLM answer with citations → evidence inspection UI → Blast Radius integration**, and wires the Copilot to the real compiled graph instead of the readiness-only stub. This is an explicit, user-approved scope override of `.planning/REQUIREMENTS.md`'s v2-deferred `AGT-01` (Qdrant RAG hybrid retrieval) and `HARD-04` (RAG retrieval precision evaluation).

Source of truth for the retrieval architecture: `AegisX-AI-Project-Bible-v6.md` Section 15 ("HYBRID GxP EVIDENCE RETRIEVAL") — already fully specifies dense+BM25 fusion, cross-encoder reranking, parent-context retrieval, graph expansion, and the exact provenance metadata fields (`evidence_id`, `document_id`, `chunk_id`, `retrieval_method`, `dense_score`, `bm25_score`, `reranker_score`, `parent_section`, `graph_path`, `regulatory_citations`). This phase implements Section 15 for real; it does not invent a new architecture.

Frontend source of truth: repo-root `UI_SPEC.md` (user-provided 2026-08-28) — supersedes/extends the per-phase UI-SPEC precedent for this phase's new surfaces (Knowledge/upload, Investigation trace, Evidence view).

</domain>

<decisions>
## Implementation Decisions

### Scope override (locked)
- **D-01:** Proceed with `AGT-01`/`HARD-04` (v2-deferred) now, ahead of Phase 7 (Hardening) and Phase 8 (Freeze). User explicitly approved this scope change 2026-08-28, aware it changes the roadmap sequence ahead of the Sep 4 submission deadline. — **Reversibility:** one-way — once phases 7/8 assume this phase's outputs exist, reverting means re-deferring a shipped subsystem, not just flipping a flag.

### Schema (locked)
- **D-02:** Extend `document_chunks` (currently `chunk_id, document_id, content, embedding_id` only, per Bible Section 4.1's literal DDL) with structure-aware columns: `section VARCHAR`, `page INT`, `parent_chunk_id UUID REFERENCES document_chunks(chunk_id)`, `chunk_index INT`, `metadata JSONB`. Document as a numbered Bible deviation in the migration file's own header comment, mirroring `llm_router.py`'s existing "Deviation N" convention (e.g. "Deviation 13: document_chunks extended with structure-aware columns for real ingestion — Bible Section 4.1's literal DDL predates Section 15's hybrid-retrieval spec and never defined a chunk hierarchy"). — **Reversibility:** reversible — additive columns, no data loss if reverted.

### Embedding provider (locked)
- **D-03:** Use a **hosted embedding API through the existing LLM router architecture** (`app/llm_router.py`'s `PROVIDER_CONFIG` pattern), not a local `sentence-transformers` model. Add a new provider config entry (or a parallel `EMBEDDING_PROVIDER_CONFIG` dict, since `call_llm`'s request/response shape is text-completion, not embeddings — planner/researcher to determine the cleanest extension that reuses the existing retry/fallback/timeout conventions rather than duplicating them). Follow the Bible's own reference to `text-embedding-004`-equivalent dimensionality (768-dim, cosine distance) for the Qdrant collection config (Bible line ~1260). — **Reversibility:** reversible — provider is swappable behind the router abstraction, by design.

### Document format scope (locked)
- **D-04:** v1 ingestion supports **PDF, DOCX, CSV, and plain text/Markdown**. CSV is structurally different (rows/columns, not prose) — needs its own parsing path, not shoehorned into the prose chunker. Plain text/Markdown requires no parsing library, useful for fast testing without needing real PDFs.

### Copilot wiring (locked, from the prior investigation this phase's directive was based on)
- **D-05:** Replace `POST /api/copilot/query`'s hardcoded `supported: False` stub with a real route that builds an `AgentState` and calls `compiled_graph.ainvoke(...)` — the exact invocation shape `tests/test_hero_loop.py` already proves works end-to-end against live Postgres+OPA. `detect_injection()` still runs first for free, since C2 is the graph's own first node — no loss of the existing injection-detection behavior.
- **D-06:** A1's stub (`run_a1` in `minimal_specialists.py`) is replaced with a real implementation that performs hybrid retrieval (dense via Qdrant + lexical via BM25) and returns ranked evidence with Section 15.7's provenance fields, rather than only validating `system_id` exists.
- **D-07:** The frontend's client-side `matchHeroQuery()` regex gate in `Copilot.tsx` is removed/relaxed once the real graph-backed route exists — free-text questions no longer need to literally contain "audit ready" + a known system id to get a real answer. The existing hero-query SSE path (`/assurance-cards/stream`, Phase 6 D-01) can remain as a fast-path optimization for the literal seeded demo query if the planner judges it valuable, but it must not be the *only* path that does real work.

### Deterministic-first boundary (non-negotiable, restated from CLAUDE.md)
- **D-08:** Retrieval (which chunks are relevant, ranking, evidence selection) may use embeddings/BM25/cross-encoder scoring — these are not compliance/RBAC/injection decisions, so they don't violate Bible Section 1.3. However, **C1's evidence verification, confidence grading, and any PASS/FAIL/compliance determination remain 100% deterministic Python/SQL/OPA**, exactly as already built. Retrieved evidence feeds C1 as an additional evidence source; it never bypasses C1 or substitutes for a deterministic check. The LLM's role is retrieval-query understanding, reranking assistance (if the reranker is itself a model call), and final answer synthesis/citation — never the verification verdict itself.
- **D-09:** Never fabricate evidence or citations (Bible Section 15's own "no LLM-invented graph relationships" rule, extended to document evidence). If hybrid retrieval + reranking produces no evidence above a relevance threshold, the Copilot must say "insufficient evidence" (per `UI_SPEC.md` Section 19) rather than answer from model knowledge alone.

### Frontend scope (locked, from UI_SPEC.md)
- **D-10:** New navigation surfaces per `UI_SPEC.md` Section 5/7: a "Knowledge" area (document upload, ingestion status, indexed knowledge list) and an "Investigation" execution view showing real retrieval stages (query understanding → semantic+lexical search → reranking → evidence → answer), per Section 9/10. These stages must correspond to actual backend operations — no decorative fake progress.
- **D-11:** Evidence View (`UI_SPEC.md` Section 11) renders each answer with inspectable evidence items (source document, section/page, retrieval method, why it was selected) — extends the existing `AssuranceCard` provenance pattern (CLAIM/EVIDENCE/RULE/CONFIDENCE) to retrieval-sourced evidence, reusing that visual language rather than inventing a new one.
- **D-12:** No new top-level nav items beyond `UI_SPEC.md` Section 5's structure (Command Centre / Investigate / Knowledge / Impact / Actions / Trust). Do not add Supplier Intelligence expansion, extra dashboards, or decorative analytics (explicit non-goals, `UI_SPEC.md` Section 29 and user directive item #12).

### Claude's Discretion
- Exact new-route name/shape for the graph-invoking Copilot endpoint (D-05) — e.g. `POST /api/copilot/investigate` vs. reusing `/api/copilot/query`.
- Exact BM25 library choice (`rank-bm25` is the obvious in-process candidate — no new service required).
- Exact cross-encoder reranker approach: a dedicated small cross-encoder model call vs. reusing an LLM-router call with a reranking-style prompt (Bible Section 15.3 says "if the selected reranking model/provider depends on configuration, follow the existing LLM routing architecture" — user directive's own wording).
- Whether the hero-query SSE fast-path (D-07) is kept as an optimization or fully retired in favor of always routing through the graph.
- Exact PDF/DOCX/CSV parsing libraries.

### Established Patterns
- Deterministic-first (Bible Section 1.3) — retrieval/reranking is new LLM-adjacent surface area; C1's verification boundary is unchanged and must stay unchanged (D-08).
- Provider-router pattern (`PROVIDER_CONFIG` + `select_provider` + graceful degradation to deterministic fallback) — the established shape to extend for embeddings, not replace.
- "Never present unverified output as real" — extends to retrieval: no evidence above threshold means an honest "insufficient evidence" response (D-09), not a fabricated answer.

### Integration Points
- New ingestion routes (upload, parse, chunk, index) are entirely new backend surface — no existing route to extend.
- New A1 implementation integrates into the existing graph via the unchanged `system_knowledge_a1` node wrapper in `app/graph/state.py` — no topology/edge changes needed, only the delegate function's internals (mirrors how A2-A6 were each built as drop-in real implementations behind unchanged node wrappers in Phase 3).
