> Per-phase validation contract for feedback sampling during execution.

## Test Infrastructure

| Property | Value |
|----------|-------|
| **Framework (backend)** | pytest 9.1.1 with respx 0.23.1 for HTTP mocking |
| **Framework (frontend)** | vitest 4.1.11 with @testing-library/react 16.3.2 |
| **Config file** | `backend/pytest.ini` (`testpaths = tests`, `pythonpath = .`); frontend uses Vite's built-in vitest integration |
| **Quick run command (backend)** | `cd backend && pytest tests/<module> -x -q` |
| **Quick run command (frontend)** | `cd frontend && npm test -- <ComponentName>` |
| **Full suite command (backend)** | `cd backend && pytest -q` |
| **Full suite command (frontend)** | `cd frontend && npm test` |
| **Estimated runtime** | backend ~90s (incl. live Postgres/OPA/Qdrant tests), frontend ~25s |

Live-service dependency: several tests in this phase exercise real Postgres, Qdrant and an
embedding API key. All of them follow `tests/test_evidence_graph.py`'s existing guard
convention and **skip with an explanatory reason** rather than failing when a service or key
is unavailable — a missing local dependency must never read as a code regression.

---

## Sampling Rate

- **After every task commit:** the task's own `<verify><automated>` command
- **After every plan wave:** `cd backend && pytest -q` and `cd frontend && npm test`
- **Before `/gsd-verify-work`:** both full suites green, plus `npx tsc -b --noEmit` and `npm run lint`
- **Max feedback latency:** 90 seconds (backend full suite); 25 seconds (frontend)

No task in any plan has a manual-only verify. Every task carries at least one
`<automated>` command, so there is no run of three consecutive tasks without automated
feedback.

## Manual-Only Verifications

Every phase behavior has automated verification. Four `<verify><human-check>` blocks exist
in addition to the automated commands, and are harvested at end of phase per
`workflow.human_verify_mode = end-of-phase`:

| Behavior | Requirement | Why Manual | Test Instructions |
|----------|-------------|------------|-------------------|
| A grounded answer actually quotes the uploaded document | RAG-06 | Asserting an LLM answer's semantic faithfulness to a source is not mechanically checkable; the automated tests assert the evidence provenance and the citation plumbing, a human confirms the answer reads as grounded | Upload `urs_extract.md` against `GXP-MFG-DEMO-01`, POST a free-text question about its contents to `/api/copilot/investigate`, confirm the answer references a real section and that each evidence item's quoted `content` appears verbatim in the source file |
| Knowledge page visual and colour compliance | RAG-01, RAG-07 | Colour-reservation and layout judgements against the UI-SPEC are visual | Visit `/knowledge`: drop zone shows its copy and Browse files is disabled until a system is picked; each of the four fixture formats reaches Ready with a nonzero indexed-unit count; a `.exe` shows the inline unsupported-type copy and adds no row; emerald appears only on the Browse files button and completed stage glyphs |
| Copilot four-scenario walkthrough | RAG-06, RAG-07 | End-to-end user experience across hero-query, grounded-answer, insufficient-evidence and injection paths | Run the four scenarios in plan 06.1-06 Task 3's `<human-check>` |
| Retrieval baseline interpretation | HARD-04 | Judging whether a measured number is *plausible* and whether the interpretation makes a real claim is editorial | Read `## Retrieval Precision Baseline (HARD-04)` in `backend/README.md` |
| Copilot-driven navigation feels like an offer, not a hijack | RAG-06, RAG-07 (D-13) | Whether 3000ms is enough time to read a notice and reach a button, and whether landing on the highlighted row feels like an answer to the question asked, are perceptual judgements no assertion captures | Run the walkthrough in plan 06.1-08 Task 3's `<human-check>` |
