# Phase 06.1 Plan 05: Knowledge Page -- Real Ingestion Front Door Summary

**A `/knowledge` page where a user selects a GxP system, uploads a document (drag-drop or Browse files), and watches its real six-stage ingestion checklist and the real indexed source list -- every rendered value traced to `POST /api/documents/upload`/`GET /api/documents`, with `apiUpload`/`uploadDocument`/`listDocuments`/`investigateCopilot` added to `lib/api.ts` for this and later plans to consume.**

## Accomplishments

- `apiUpload<T>()`: the multipart sibling of the existing `apiPost<T>`, reusing `ApiError`/`parseErrorDetail`/`identityHeaders` verbatim, no manual `Content-Type` (the browser derives the multipart boundary from the `FormData` instance)
- `uploadDocument`/`listDocuments`/`investigateCopilot` wired to `POST /api/documents/upload`, `GET /api/documents`, `POST /api/copilot/investigate` respectively
- Seven new typed interfaces in `lib/api.ts` mirroring `backend/app/schemas.py` field-for-field, including nullability (`| null`, never `?`) and D-13's address-free `NavigationTarget` with a closed `kind: 'document' | 'graph_node'` literal union
- `Knowledge.tsx`: a hand-built Tailwind v4 page (no new component/icon library, continuing the phase's shadcn-declined precedent) -- system selector (no "All Systems" option, since a document must belong to exactly one system for graph expansion), drop zone with client-side extension pre-check, inline 413/415 error copy distinguished from `ApiError.status`, and a source list rendering a real six-stage ingestion checklist per row
- Stage-honesty implementation (D-10): no `setTimeout`/`setInterval` anywhere in the file; the checklist is derived only from local in-flight state and the upload response's own `status`/`failed_stage`, since there is no per-stage push channel for this synchronous upload call
- One new flat top-level `/knowledge` route in `routes.tsx`, picked up automatically by `NavBar.tsx`'s existing `routes.map()` rendering -- no `NavBar.tsx` change needed
- 21 new named tests (9 in `api.test.ts`, 12 in `Knowledge.test.tsx`) plus 2 updated route-table tests; full frontend suite green at 173 passed (159 pre-existing + 14 net new after accounting for the routes.test.tsx heading-list addition), no regressions

## Decisions Made

- **`uploadDocument`/`listDocuments`/`investigateCopilot` declared `async`, diverging from the file's existing non-async-delegator convention** (`fetchEvidenceGraph`, `queryCopilot`, etc. are plain `export function` returning the inner promise). The plan's own acceptance criteria greps for `export async function uploadDocument\|export async function listDocuments\|export async function investigateCopilot\|export async function apiUpload` matching all four -- an explicit, testable contract takes precedence over the file's implicit style precedent for these three functions specifically.
- **`CopilotFinding` added as a new exported interface**, not named in the plan's own artifact list, to give `CopilotInvestigateResult.findings` a real type (mirroring `backend/app/schemas.py`'s `AgentFinding`) instead of leaving it untyped or `unknown[]`.
- **Knowledge.tsx's source list is unfiltered by the upload system selector.** Cross-checked against `06.1-08-PLAN.md` (owns `?system=`/`?document=` deep-link preselection and row highlighting "after plan 06.1-05") to confirm the system `<select>` here is upload-target-only, not a source-list filter -- `listDocuments()` is called with no `system_id` argument so the page shows the full indexed corpus.
- **A FAILED document's stage checklist uses a locally-cached `failed_stage`, keyed by `document_id`, populated from the upload response** -- not from `GET /api/documents`'s `DocumentSummary.failed_stage`, which `06.1-04-SUMMARY.md` documents is always `None` at read time (the route "never guesses" a stage it cannot know). A document that failed ingestion in a session prior to the current page mount therefore renders an honest `FAILED` status with no specific stage highlighted -- the true limit of what the server currently reports, not a client-side gap this plan could close without changing the backend contract (out of scope here).
- **A failed stage's glyph uses `✕` in `text-red-400`**, not explicitly named in `06.1-UI-SPEC.md`'s three-glyph legend (`✓`/`◌`/`-`) but consistent with the Color table's Destructive-hue reservation for "ingestion-failure errors" -- the acceptance criteria's emerald-usage grep does not constrain this choice, and no other codebase convention existed to reuse instead.
