# Phase 6 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** Covers the two UI-facing requirements this phase closes — UI-03 (Command Centre dashboard: `frontend/src/pages/CommandCentre.tsx`, currently a static placeholder) and UI-04 (Ask GxP Copilot chat + live agent topology: `frontend/src/pages/Copilot.tsx`, currently a bare WebSocket echo-test stub) — plus the Guided Tour (SENT-5-08, P0, a new cross-page overlay component). It does not cover `Actions.tsx` (Phase 5, already specified in `05-UI-SPEC.md`) or `TrustCentre.tsx`/`AssuranceLab.tsx`/`Suppliers.tsx`/`InspectionSimulator.tsx` (FE-02/03/04/05, v2, explicitly out of scope — this phase's Guided Tour reuses their *absence* as a constraint, routing its "Audit Integrity" beat back to the Command Centre rather than building a new Trust Centre surface).

**shadcn gate — decision:** No `components.json` exists in this repo (confirmed again this session), and the stack is React + Vite. Per the shadcn gate this would normally prompt initialization. **Declined again**, continuing the precedent set explicitly in `05-UI-SPEC.md`: five phases (2 through 5) have shipped a consistent, hand-built Tailwind v4 dark design system with no component library. `06-RESEARCH.md`'s own Alternatives-Considered analysis reached the same conclusion independently: adopting React Bits (this repo's separate animation-guidelines doc's named tool) means bootstrapping via the shadcn CLI *and* adding `framer-motion` as a runtime dependency, which was flagged `[SUS: too-new]` by the package-legitimacy checker and would require a `checkpoint:human-verify` gate before install. Continuing to decline shadcn is the lower-risk, precedent-consistent choice.

**Named tension, resolved here (not deferred again):** The user's memory record (`ui_animation_guidelines.md`, 2026-08-23) explicitly flags Phase 6 as "most likely the guided-tour/demo phase" where the no-component-library precedent and the user's stated "buttery smooth" animation intent would collide. This UI-SPEC resolves it with two separate decisions instead of one all-or-nothing call:
1. **Guided Tour engine:** adopt `react-joyride` (3.2.0) as a scoped, standalone **npm exception** — not a shadcn/React Bits adoption. It is a plain npm package with no shadcn CLI dependency and no `framer-motion` transitive dependency; installing it does not initialize shadcn and does not touch the declined-component-library precedent for the rest of the app. Package-legitimacy verdict: **OK** (`06-RESEARCH.md` Package Legitimacy Audit — 1,380,658 weekly downloads, actively maintained, confirmed React 19 peer support). This is the "exception worth taking" the research flagged: cross-viewport spotlight/tooltip positioning with scroll-into-view and resize handling is a deceptive-complexity problem this project's own philosophy (Don't Hand-Roll) warns against reinventing, and no existing hand-rolled component in this codebase attempts it.
2. **Everything else (Command Centre, Copilot chat, topology canvas, mini-cards):** stays hand-built Tailwind, with animation delivered via **CSS-only Tailwind transition utilities** (see Animation Contract below) — no `framer-motion`, no React Bits, no shadcn. This satisfies the animation guidelines' own priority order ("professional design > clear UX > performance > visual polish > animation") and its explicit requirement that "all animations must follow existing color/typography/spacing/component style" — a CSS-transition-only approach is definitionally unable to violate that, whereas a new animation library risks introducing a second visual language mid-hackathon.

If the user wants richer motion (spring physics, staggered orchestration) after this phase, that is an explicit, separate decision to make with a human `checkpoint:human-verify` on `framer-motion` — not something to bundle into this contract by default.

## Spacing Scale

Declared values (multiples of 4), identical to `05-UI-SPEC.md` — no new scale introduced:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-free inline gaps, badge micro-padding |
| sm | 8px | Compact element spacing (chat bubble internal gaps, mini-card internal `gap-2`) |
| md | 16px | Default element spacing (`mt-4`, card `p-4`) — mini-card grid gap, chat message vertical rhythm |

| 2xl | 48px | Reserved — not used this phase |
| 3xl | 64px | Reserved — not used this phase |

Exceptions:
- Readiness dial SVG: fixed `160px × 160px` viewport (not a spacing token — a component dimension). - Chat bubble max-width: `max-w-2xl` (matches the existing page-intro paragraph max-width convention already used in `CommandCentre.tsx`/`Copilot.tsx` placeholders) — keeps chat readable without a hand-tuned new breakpoint.

## Animation Contract

*(Non-template section — resolves the animation-guidelines tension flagged in `06-RESEARCH.md` and the user's `ui_animation_guidelines.md` memory. Load-bearing for planner/executor, same status as `05-UI-SPEC.md`'s "Interaction Notes".)*

**Approach: CSS-only Tailwind transitions, no new runtime dependency** (except `react-joyride`'s own internal positioning/scroll logic, which is not a general animation library). This satisfies the animation-guidelines doc's stated priority order (professional design > clear UX > performance > visual polish > animation) and its "must follow existing color/typography/spacing" rule by construction — there is no second design language to drift from.

| Surface | Animation | Implementation | Constraint |
|---------|-----------|-----------------|-----------|
| Command Centre mini-cards, on mount | Subtle fade-in + 4px slide-up | `transition-all duration-300 ease-out` from an initial `opacity-0 translate-y-1` state to `opacity-100 translate-y-0`, staggered ~40ms per card via inline `style={{ transitionDelay }}` (no stagger library) | ≤300ms total per card; never blocks interactivity — cards are clickable/readable immediately, animation is purely cosmetic |
| Readiness dial, on value change | Animate the SVG arc's `stroke-dashoffset` | CSS `transition: stroke-dashoffset 500ms ease-out` on the arc `<circle>` | Only animates on data change, not on every re-render (guard with the previous value in state) |
| Chat message, on arrival | Fade-in (no slide, to avoid layout jank as `AssuranceCard`s stream in one after another per D-05) | `transition-opacity duration-200` from `opacity-0` to `opacity-100` | Must not delay the card's actual content from being readable — animation is decorative only |
| Topology node status change (waiting→running→complete) | Color transition | `transition-colors duration-300` (already the exact class NavBar.tsx uses for its active-state transition — direct reuse, not a new pattern) | This is the "animate agent and verification states" requirement from Bible §14.4 Step 1/4 — satisfied without any new library |
| Buttons (Ask Copilot, tour Next/Skip, mini-card hover if any) | Hover background/opacity shift | `transition-colors` / `transition-opacity`, matching `NavBar.tsx`'s exact existing convention | No scale/shadow-elevation effects this phase (keeps parity with the flat, no-shadow visual language every prior page uses) |
| Guided Tour spotlight/tooltip | `react-joyride`'s built-in scroll-into-view + fade transition | Library default (`disableScrolling: false`), themed via the `styles.options` prop — see below | This is the one surface where the library's own motion (not hand-rolled CSS) is the mechanism, per the "exception worth taking" decision above |

**`react-joyride` theming (must match the existing palette exactly, not its default light theme):**
```
options: {
  arrowColor: '#0f172a',        // slate-900, matches secondary surface
  backgroundColor: '#0f172a',   // slate-900
  overlayColor: 'rgba(2, 6, 23, 0.75)', // slate-950 @ 75%
  primaryColor: '#059669',      // emerald-600, matches accent
  textColor: '#f1f5f9',         // slate-100, matches body text on dark surfaces
  spotlightShadow: '0 0 0 4px rgba(5, 150, 105, 0.4)', // emerald-600 glow, not a new hue
}
```

**Explicit non-goals this phase** (per the animation-guidelines doc's own "Avoid" section and to keep `framer-motion` out of scope): no floating/particle effects, no gradient backgrounds, no spring-physics easing, no page-transition library, no skeleton-shimmer components. The product must look and read as professional with all CSS transitions disabled — animation here is confirmably a "supporting layer," never the mechanism by which information is conveyed.

**Readiness dial computation (resolves anti-pattern flagged in `06-RESEARCH.md`):** Never reads `gxp_systems.readiness_score` (static seed literal, 61/94, never recomputed). Computed client-side as `passed_checks / total_checks` across both systems' `assurance-cards` responses (4 checks × 2 systems = 8 total in the default "All Systems" view). Color banded per the Color table above (≥80% emerald, 50-79% amber, <50% orange).

**System selector placement (resolves "Claude's Discretion"):** Dashboard-level control at the top of `CommandCentre.tsx`, directly below the page heading — not per-card. Options: "All Systems" (default, aggregates both), "GXP-MFG-DEMO-01", "BUS-IT-DEMO-02". **Non-hero-query chat path (resolves "Claude's Discretion" — backend vs. client-only):** Wired through a real backend call, not a client-side string. A small new endpoint (or inline logic in a new `POST /api/copilot/query`-shaped route, planner's call on exact shape) calls `detect_injection()` (`backend/app/agents/c2_gateway.py`, already built/tested, zero-LLM) on any free-text input that doesn't match the hero-query shape. If `detect_injection()` returns a reason, render the injection-detected Copywriting Contract row with that real reason string. Otherwise render the honest "not supported yet" row. This choice is made specifically because it gives Guided Tour Step 6 ("AI Safety") a real, deterministic backend call to demonstrate — a client-only guard would leave that beat with nothing real to show, undercutting D-08's "REAL backend calls" requirement.
