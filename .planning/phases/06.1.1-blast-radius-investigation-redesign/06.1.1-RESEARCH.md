# Phase 06.1.1: Blast Radius Investigation Redesign — Research

**Method:** Direct code inspection (Read) of every file CONTEXT.md names as canonical, plus the real backend/frontend type contracts. No web research was needed — this is a redesign of already-shipped, already-correct code; the open questions are about the current implementation's exact shape, not about unfamiliar technology.

## Current State (verified against code, not CONTEXT.md's description alone)

### `BlastRadius.tsx` (188 lines)
Three-state machine (`loading`/`error`/`ready`), system selector (`SYSTEM_OPTIONS` hardcoded to the two demo systems — unchanged by CONTEXT.md), `?node=` deep-link via `useSearchParams`, a system-change effect that clears node selection (guarded by `isFirstSystemChange` ref so an initial deep link survives mount), and a `?node=`-driven blast-radius fetch effect. Layout: `grid-cols-1 lg:grid-cols-3` — graph spans 2 cols, detail+summary panels stack in the third. **No `?system=` deep-link param exists yet** — CONTEXT.md's D-08 says this already exists, but it does not: the system id comes only from local `SYSTEM_OPTIONS` state, seeded from `?system=` only via a validated initial-state read (line 27-32) — there is no corresponding *write* of `?system=` on selector change, and no code reads a second `?origin=` param. Confirms D-08's "Claude's discretion" framing was correct to leave open; CONTEXT.md's own D-08 text is imprecise about what "already exists" — only the *read* half exists.

### `EvidenceGraphCanvas.tsx` (84 lines)
Pure presentational wrapper over `@xyflow/react`. `toFlowNodes` uses a deterministic `COLUMNS=6` grid layout (no force-directed/dagre). Node `data.label` is literally `node.node_id` (`"{node_type}:{entity_id}"` — a colon-separated raw id, not a human label). Selection is React Flow's own `selected` flag plus `borderWidth: 3` — no color coding of any kind. **`proOptions` is not set at all** — confirms D-05's watermark bug is real and is a one-line fix (`proOptions={{ hideAttribution: true }}` on the `<ReactFlow>` element, line 73-81).

### `NodeDetailPanel.tsx` (59 lines) / `BlastRadiusPanel.tsx` (123 lines)
Both pure presentational, no fetch, no derived computation beyond `Object.entries()` and an `allEmpty` boolean. `NodeDetailPanel` renders every `node.properties` key/value as a generic `<dl>` — no per-node-type field curation (matches D-02: properties are a fixed allowlisted column set server-side, but the client currently renders them generically rather than with type-aware hierarchy). `BlastRadiusPanel` renders the exact Bible §14.3 four-line impact summary shape (direct/indirect dependencies, affected controls, potential GxP impact) plus five `affected_*` list sections and a highest-impact-downstream line — every number is `.length` of a server array, confirming D-04's "real counts only" constraint is already satisfied by the *existing* summary numbers; the redesign's job is presentation/IA, not correctness.

### Data shapes (verified in `frontend/src/lib/api.ts`)
```ts
EvidenceGraphNode   { node_id, node_type, entity_id, properties: Record<string, unknown> }
EvidenceGraphEdge   { source_id, target_id, relation_type }
EvidenceGraphResponse { system_id, nodes: EvidenceGraphNode[], edges: EvidenceGraphEdge[] }
BlastRadiusResponse {
  system_id, source_node_id,
  direct_dependencies: string[]      // node_ids
  indirect_dependencies: string[]    // node_ids
  affected_requirements/tests/risks/changes/controls/systems: string[]  // node_ids or entity labels (see below)
  potential_gxp_impact: string
  highest_impact_downstream: string | null
}
```
**Open question resolved (confirmed by reading `blast_radius()` at `backend/app/graph/evidence_graph.py:552-597`):** every entry in `direct_dependencies`, `indirect_dependencies`, and all five `affected_*` lists is a real graph `node_id` (`"{node_type}:{entity_id}"`, built via `_by_type()` from `sorted(n for n in all_downstream if ...)` where `n` is always a `G` node id) — never a human label. This means D-07's client-side path highlighting can match these strings directly against `EvidenceGraphNode.node_id` with no additional lookup or backend change.

### D-03 confirmed for real: no per-edge evidence field
`EvidenceGraphEdge` is exactly `{ source_id, target_id, relation_type }` — no citation/evidence field exists anywhere in the graph response. The "why is this connected" UI must be built entirely from `relation_type` + both endpoint nodes' own `properties`. This is a hard constraint, not a simplification the planner should second-guess.

### D-09 Copilot-navigation: infrastructure already exists, no new backend work needed
`frontend/src/lib/navigation.ts` (92 lines, shipped in Phase 06.1 plan 06.1-08) already contains:
- `NAVIGATION_ROUTE_BUILDERS.graph_node` — builds `/blast-radius?system=…&node=…` from a `NavigationTarget`
- `evidenceHref()` — for any `RetrievalEvidenceItem` with `evidence_type: 'graph_relationship'`, resolves the *terminal* node of its `graph_path` and returns a Blast Radius deep link
- Backend's `NavigationTarget` (`kind: 'document' | 'graph_node'`) is computed deterministically server-side by `compute_navigation_target()` (a pure function, no LLM/no I/O — verified in 06.1's own VERIFICATION.md truth #8) and only returned when every citation in an answer resolves to one unambiguous destination

**This means D-09 is already ~80% satisfied by Phase 06.1's shipped work**, not something 06.1.1 must build from scratch: if a user asks the Copilot "what's the blast radius of RISK:R-004" (or similar) and the retrieval pipeline surfaces a `graph_relationship` evidence item whose path terminates at that node, the existing `navigation_target`/`AutoNavigateNotice` machinery already computes a `kind: 'graph_node'` target and the existing `?node=` deep-link on `BlastRadius.tsx` already honors it. **What remains for 06.1.1's D-09 requirement is verification, not new construction**: (1) confirm this end-to-end path actually fires for a "show me the blast radius of X" phrasing against a live document/graph (not assumed), (2) confirm the landing state is the *redesigned* investigation view (post D-04) with the origin node correctly pre-selected/highlighted, not just a generic node click. If live verification finds a genuine gap (e.g., the retrieval pipeline never surfaces a `graph_relationship` evidence item for a pure "show blast radius" imperative rather than a factual question), that is a real, reportable gap per D-09's own instruction — not something to fake with new backend intent classification, since that would exceed this phase's frontend-only mandate (D-12) and reopen Phase 06.1's already-verified scope.

### Reusable visual precedent: `AssuranceCard.tsx`
Referenced in CONTEXT.md as a precedent for the "why is this affected" section. Its CLAIM/EVIDENCE/RULE three-part card pattern is a reasonable structural analog for a relationship-explanation card (`RELATIONSHIP: RISK:R-004 —ASSOCIATED_WITH→ SYSTEM:GXP-MFG-DEMO-01` / properties of both ends), even though the underlying data source differs (D-03: no retrieval evidence exists for graph edges, only relationship-type + properties).

## Client-Side Path Highlighting (D-07)

The backend's own `blast_radius()` traversal is not re-exposed as a path (only as flat sets: direct/indirect/affected_*). A "highlight the path back to the origin" feature requires the client to compute this itself over the *already-fetched* `EvidenceGraphResponse.edges` array (build an adjacency list once per graph load, BFS/shortest-path from the selected node to the origin/root on click) — this is real, bounded, client-side graph work (NetworkX-equivalent in TypeScript over a graph the response already proves is small enough to render in a single React Flow canvas — Phase 4's data shows single-digit-to-low-dozens node counts for the demo systems). No new library needed; a plain BFS over an adjacency map is sufficient and testable in isolation (pure function, no React, no fetch).

## Non-findings / confirmed non-gaps

- No new backend endpoint is needed for the core redesign (D-04 through D-08) — every number and relationship the new UI needs is already in `EvidenceGraphResponse` + `BlastRadiusResponse`.
- `evidence_graph.py` graph construction is out of scope and was not modified or even flagged as needing modification — the only backend-adjacent read is the one-time confirmation of `affected_*` string format noted above (read-only, no edit).
- No conflicting documentation was found — Bible §14.3, `UI_SPEC.md` §13/23/25, and the current code agree on what data exists; the only imprecision found was CONTEXT.md's own D-08 claim about `?system=` already round-tripping, corrected above.

## Recommendation for planner

Plan as a tracer-first vertical slice sequence:
1. **Tracer (Wave 1):** investigation header + impact summary card (using existing `BlastRadiusResponse` fields, restructured IA) + `proOptions={{hideAttribution:true}}` fix + basic semantic node coloring by node_type-derived state (neutral/highlighted/warning/critical/verified) — the smallest change that proves the new IA end-to-end on real data.
2. **Wave 2:** investigation panel replacing `NodeDetailPanel`'s generic property dump with curated, type-aware relationship explanation (D-03's real fields only) + client-side path highlighting (D-07) built as a pure, unit-testable traversal function.
3. **Wave 3 (gated):** D-09 Copilot-navigation verification — live end-to-end check that an existing-infrastructure navigation actually lands correctly on the redesigned page with the right node pre-selected/highlighted; fix only if a genuine gap surfaces, report if the gap requires backend work.

`?system=` write-support (completing D-08's round-trip) belongs in Wave 1 alongside the header, since the header needs to display "what are we investigating" including the system context in a shareable/deep-linkable URL.
