# Phase 06.1.1: Blast Radius Investigation Redesign - Context

**Gathered:** 2026-08-28 (via direct user directive — two consecutive detailed requirement documents pasted by the user — plus assistant repo-inspection grounding it against real code)
**Status:** Ready for planning

<domain>
## Phase Boundary

The current `/blast-radius` page (`frontend/src/pages/BlastRadius.tsx`, 178 lines + `EvidenceGraphCanvas.tsx` 84 lines + `BlastRadiusPanel.tsx` 123 lines + `NodeDetailPanel.tsx` 59 lines) is functionally real — it already has system selection, a deep-link `?node=` query param, loading/error/empty states, and calls the real backend (`GET .../evidence-graph`, `GET .../blast-radius?node_id=`) — but is visually and experientially thin: bare React Flow canvas with the default attribution watermark visible, small unstyled nodes, and a "click a node" passive panel rather than an investigation narrative.

This phase redesigns the **frontend investigation experience** around the already-real backend graph (`backend/app/graph/evidence_graph.py`) — it does not rebuild the graph construction logic, which is correct and unchanged. It also adds one small, explicitly-gated integration: the Copilot resolving a plain-language Blast Radius request and navigating the user into a focused investigation state.

**No new backend endpoints are anticipated** for the core redesign — `GET .../evidence-graph` and `GET .../blast-radius` already return everything the new UI needs (nodes with `node_type`/`entity_id`/`properties`, edges with `relation_type`, and the blast-radius traversal result). If the planner/researcher discovers a genuine gap (e.g. no per-edge evidence/citation data exists to satisfy "why is this affected"), it must be reported as a real dependency, not faked — see D-09 below.

</domain>

<decisions>
## Implementation Decisions

### Real data model (verified against code, not invented)
- **D-01:** The actual graph has 14 node types (`SYSTEM, DOCUMENT, TEST_CASE, TEST_RESULT, REQUIREMENT, RISK, DESIGN_ELEMENT, INCIDENT, ACCESS_REVIEW, ACCESS_RECORD, SUPPLIER, SUPPLIER_ASSESSMENT, PERIODIC_EVALUATION, CHANGE, CHANGE_ACTION`) and 7 relation types (`VERIFIED_BY, HAS_RESULT, HAS_ACTION, ASSESSED_BY, GOVERNS, ASSOCIATED_WITH, AFFECTS`) — frozen allowlists in `evidence_graph.py`'s `NODE_SPECS`/`RELATION_TYPES`. A `CHANGE` node's `AFFECTS` edges reach exactly `{REQUIREMENT, TEST_CASE, DOCUMENT, DESIGN_ELEMENT, RISK}` (`CHANGE_AFFECTS_ENTITY_TYPES`), and `REQUIREMENT --VERIFIED_BY--> TEST_CASE` is a separate real edge — so the user's example chain (Change → Design Element / Requirement → Test → Risk) is a real, traceable multi-hop path through actual data, not something to invent.
- **D-02:** Node ids are `"{node_type}:{entity_id}"` (`make_node_id`/`split_node_id`). Node `properties` are a fixed allowlisted column set per type (e.g. `RISK` exposes `risk_summary, severity, probability, owner`) — the redesigned node/panel UI must render from these real properties, never fabricate additional fields.
- **D-03:** No per-edge "evidence" or "citation" field currently exists in the graph response (`EvidenceGraphResponse`'s edges are just `source_id/target_id/relation_type`) — the "why is this connected" answer for now IS the relationship type + the two entities' own properties (e.g. "this RISK is ASSOCIATED_WITH this SYSTEM"), not a separate evidence document. Do not fabricate an evidence/citation UI element the backend doesn't back. If Phase 06.1's retrieval evidence should eventually attach to graph relationships, that is future integration, not this phase's job — see Deferred.

### Redesign scope (locked, from user directive)
- **D-04:** Rebuild the information architecture, not just re-skin the existing page: investigation header (what are we investigating), impact summary (real counts only — affected entities, risks, requirements/tests affected — computed from the actual blast-radius response, never invented), main graph, investigation panel (replaces "click a node" placeholder with real always-useful content), evidence/relationship explanation using D-03's real fields, investigation-path highlighting.
- **D-05:** Hide the React Flow attribution watermark (`proOptions={{ hideAttribution: true }}` on the `<ReactFlow>` element in `EvidenceGraphCanvas.tsx`) — a one-line, real, verifiable fix for one of the user's explicit complaints.
- **D-06:** Node visual design: larger, readable nodes with clear type/identifier/description hierarchy; semantic (not decorative) color — neutral/context, highlighted/investigation-path, warning/potential-impact, critical/high-impact, verified/evidence-backed as distinct visual states per `UI_SPEC.md` Section 23. Entity types visually distinguishable without becoming "a rainbow of colors" (user's explicit phrase).
- **D-07:** Selecting a node must dim/de-emphasize unrelated nodes and highlight the path back to the origin (investigation-path mode) — real graph traversal (NetworkX shortest-path or the same traversal the backend already proves in `blast_radius`), computed client-side over the already-fetched graph data, not a new backend call per click.
- **D-08:** Deep-linking already exists (`?node=`) — extend it to also carry the originating "change" context if the user's "investigation origin" concept requires a second param (e.g. `?system=&node=&origin=`), reusing the existing `useSearchParams` pattern in `BlastRadius.tsx` rather than inventing new routing infrastructure.

### Copilot integration (locked, but explicitly gated)
- **D-09:** The Copilot resolving "show me the blast radius of X" and navigating the user into a focused, pre-selected Blast Radius state is REQUIRED per the user's directive — but it is gated on Phase 06.1 (Advanced Retrieval & Real Copilot) actually routing the Copilot through the real orchestrator/entity-resolution path first. **Do not build this on top of the current `matchHeroQuery()` regex stub or the `supported: false` stub route** — that would be exactly the "fake it" shortcut both directives explicitly forbid. This phase's plan for the Copilot-navigation feature must have `depends_on` pointing at the relevant Phase 06.1 plan(s), and if 06.1 hasn't landed yet when this phase is planned, the plan-checker should either sequence this as the last wave or flag it as blocked, not silently stub it.
- **D-10:** If the user is ambiguous about which entity/change they mean, the Copilot must ask a clarification question — never silently pick one (explicit user instruction, and consistent with the project's existing "never fabricate/never guess" discipline).

### Non-goals (locked, from user directive)
- **D-11:** No new decorative UI (glassmorphism, gradients, glowing borders, generic metric cards). No feature-bombing — every panel element must answer one of the 7 questions the user listed (what changed / what's affected / how connected / why affected / what evidence / how serious / what next).
- **D-12:** Do not rewrite the backend graph-construction logic (`evidence_graph.py`) unless the researcher finds a genuine, reported gap — this phase is frontend-first.

### Claude's Discretion
- Exact component boundaries (new components vs. extending `EvidenceGraphCanvas.tsx`/`NodeDetailPanel.tsx`/`BlastRadiusPanel.tsx` in place).
- Exact path-highlighting algorithm (client-side NetworkX-equivalent graph traversal in TypeScript, or reusing the backend's own blast-radius response shape more directly).
- Exact impact-summary metric set, as long as every number is traceable to a real field in the existing API responses.
- Whether `?origin=` is a real new query param or the existing `?node=` alone is sufficient framing for "investigation origin" (D-08).

</decisions>
