<objective>
Wire the FastAPI backend to the live OPA sidecar: an async client that POSTs a payload to the real policy endpoint and returns the violations OPA produced, with a fallback path that keeps the caller alive when OPA is not answering.

This plan covers Build-Map ticket **SENT-1-04** (OPA Docker sidecar wired to app). Per BRANCHING.md §4 it owns "the backend OPA client module and its `python_fallback_rules()` stub", and per BRANCHING.md §6 it may not start until SENT-1-03 is closed — hence wave 2, depending on plan 02-02 for the rules and plan 02-03 for the application tier and its test fixtures.

Purpose: this function is the seam where the deterministic policy engine becomes reachable from application code. In Phase 3, C1's `calculate_confidence()` consumes its output as one of the two independent evidence sources — the other being the database record — that make a verified finding verified. If this returns a mock, the product's entire thesis is hollow.

Output: One module, one test file, and a documented, tested failure path.
</objective>

  <action>
Create `backend/app/opa_client.py` implementing the Bible Section 3.4 pair.

`evaluate_opa_policy(payload: Dict[str, Any]) -> List[Dict[str, Any]]` is `async`, opens an `httpx.AsyncClient`, POSTs a body of `{"input": payload}` with `timeout=2.0`, calls `raise_for_status()`, and returns `response.json().get("result", [])`. Keep every one of those specifics. The timeout value in particular is a stated Bible constant, and A0's fan-out budget in Phase 3 is built around policy calls returning fast.

`python_fallback_rules(payload: Dict[str, Any]) -> List[Dict[str, Any]]` returns an empty list. The Bible states outright that its body is omitted for brevity, and SENT-1-04's contract requires only that the stub exist. Do not reimplement the 10 rules in Python here. A second, independently drifting copy of the compliance logic is worse than no copy: it would produce two answers to the same regulatory question with no mechanism keeping them equal, which is precisely the failure mode the deterministic-first architecture exists to eliminate. Give the function a docstring saying exactly that, and stating that mirroring the Rego logic is deferred to a phase that has a genuine requirement for offline evaluation.

Three deviations from the Bible's literal text, each with a stated reason, each recorded in Task 2:

1. **Configurable endpoint.** The Bible hardcodes `http://localhost:8181/v1/data/sentinel/gxp/violation`. Read the value from an `OPA_URL` environment variable, defaulting to that same path. In normal operation the behaviour is identical. This is not a style preference: the fallback branch cannot be exercised at all without pointing the client somewhere that does not answer, and stopping the shared OPA container mid-suite to force it would be far worse. Use `127.0.0.1` rather than `localhost` in the default, to sidestep the IPv6-first resolution that makes `localhost` intermittently slow on Windows.

2. **HTTP error statuses route to the fallback as well.** The Bible catches `httpx.RequestError`, but its own `raise_for_status()` call raises `httpx.HTTPStatusError`, which is not a subclass of `RequestError` and would therefore escape uncaught. An OPA that answers with a 500 or a 400 is exactly as unusable to the caller as one that does not answer at all, and letting the exception propagate would take down the agent that called it — the precise opposite of what a fallback is for. Catch both and route both to `python_fallback_rules()`. Note in a comment that `httpx.TimeoutException` already inherits from `RequestError` and therefore needs no separate branch.

3. **Log, do not print.** The Bible's failure branch calls `print()`. Use a module-level `logging.getLogger(__name__)` at warning level, including the exception text and the URL that failed. A server process writing diagnostics to stdout loses them the moment it runs anywhere other than a developer's terminal.

Return the raw dicts OPA produced rather than constructing `OPAViolation` instances: the Bible's signature returns `List[Dict[str, Any]]`, and Phase 3's C1 verifier is the component that decides how to type and score them. State in the module docstring that the dict keys match `app.schemas.OPAViolation` exactly, so a caller wanting validation can construct one directly.

Import nothing from `app.main`. This module must be importable on its own, and a circular import would break both.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| backend process -> OPA REST on 127.0.0.1:8181 | The application asks an external process for a compliance decision and trusts the answer. This is the boundary the whole deterministic-first architecture rests on. |
| agent-supplied payload -> OPA input document | In Phase 3 the payload will be assembled from database rows in response to a user query, so untrusted-influenced data begins crossing here. |
| OPA response -> application logic | Whatever comes back is treated as ground truth about regulatory compliance. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-19 | Spoofing | a fallback that silently returns "compliant" | high | mitigate | An empty-list fallback is indistinguishable from a genuine clean evaluation, and in this product that reads as an audit pass. Mitigated by requiring the warning log on every fallback and asserting it with `caplog`, so the degradation always leaves a trace. Phase 5's audit trail records `opa_rule_ids` per event, which makes a fallback-produced empty result visible after the fact rather than invisible. |
| T-02-20 | Tampering | a substituted OPA endpoint | medium | mitigate | `OPA_URL` is read from the environment, which is a genuine new lever: a wrong value silently redirects every compliance decision. The default is a loopback address, no code path writes it, and it is documented in `backend/README.md`. Loopback-only publishing was verified live in 01-VERIFICATION.md truth 3. |
| T-02-21 | Denial of Service | a hung OPA call blocking a request | medium | mitigate | The Bible's 2.0-second timeout is preserved and asserted by grep. `httpx.TimeoutException` inherits from `RequestError` and therefore already routes to the fallback, so a slow sidecar degrades rather than stalls. |
| T-02-22 | Elevation of Privilege | an uncaught status error crashing the agent | medium | mitigate | This is deviation 2's whole purpose: the Bible's own `raise_for_status()` raises a class its own `except` clause does not catch. Both branches now route to the fallback, and both are covered by a test. |
| T-02-23 | Tampering | injection into the OPA input document | low | accept | In this phase every payload is test-authored. Rego evaluates data, not code, so an input document cannot alter rule logic. Sanitisation of agent-assembled payloads becomes relevant in Phase 3 and is gated by C2 in Phase 5 (SAFE-01, SAFE-02). |
| T-02-SC | Tampering | package-manager installs | high | mitigate | This plan installs no package. `httpx` was installed and audited in plan 02-03 and carries an `OK` verdict in 02-RESEARCH.md lines 117-137. `pytest-asyncio` is explicitly declined because it is absent from that table and is not needed. |
</threat_model>
