<objective>
Wire continuous integration: a GitHub Actions workflow that stands up the real Compose stack and runs every gate this phase produced, on every pull request and every push to `main`.

This plan covers Build-Map ticket **SENT-1-09** (CI test runner), the only P1 ticket in Stage 1. Its contract is explicit about timing: "every PR from Stage 2 onward runs schema + Rego + basic API tests automatically". Stage 2 is Phase 3, so CI has to exist before Phase 3 starts — which is why it belongs at the end of this phase rather than deferred.

Per BRANCHING.md §4 it owns `.github/workflows/`. It sits in wave 3 because it invokes what waves 1 and 2 built; a workflow written earlier would reference scripts that do not yet exist and be red from its first run, which trains everyone to ignore it.

The design principle throughout: CI invokes the developer-facing gate scripts rather than reimplementing their assertions in YAML. A workflow that maintains its own separate idea of what "passing" means drifts from the local one, and then a green CI badge stops meaning anything.

Purpose: from Phase 3 onward, agents write real compliance logic against a schema, a seed set, and a rule bundle that must stay correct. CI is what makes a regression in any of them visible within minutes instead of at demo time.
Output: One workflow file.
</objective>

  <action>
Create `.github/workflows/ci.yml`.

Trigger on `pull_request` against any branch and on `push` to `main`, matching BRANCHING.md's trunk-based model where short-lived ticket branches merge back by PR. Add a `concurrency` group keyed on the ref with `cancel-in-progress: true`, so a rapid second push does not leave two runs competing for the same Docker daemon.

Define two jobs.

**Job `backend-and-policy`**, on `ubuntu-latest`, with a `timeout-minutes` ceiling so a hung container cannot burn the runner budget:

1. Check out the repository.
2. Create the environment file the way the documented Quickstart does: copy `.env.example` to `.env`, then substitute a CI-only value for `POSTGRES_PASSWORD`. Copying the committed template rather than writing a bespoke env block means CI exercises the same path a new developer follows, so a drifted `.env.example` fails here instead of silently only failing for humans.
3. Bring the stack up with `docker compose up -d --wait`, then run `bash infra/health-check.sh`. Bring up all three services rather than only the two Stage 1 needs: Phase 1's ENV-01 gate is "all three healthy from one command", and a CI job that skips Qdrant would let a regression in that gate through unnoticed. This step also exercises both derived image builds.
4. Data tier: `bash infra/verify-schema.sh`, then `bash infra/apply-seed.sh`, then `bash infra/verify-seed.sh`. Schema verification runs before seeding because a cold `up` has just executed the initdb DDL and nothing has been seeded yet — that ordering is what makes each gate's failure message point at one cause.
5. Policy tier: `bash policies/opa-gate.sh`. This runs `opa test` through `docker compose exec` against the running container and then probes the REST endpoint, so it needs no `opa` binary installed on the runner.
6. Set up Python at the version local development uses, and install `backend/requirements.txt`. Do not create a `backend/.venv` in CI: a runner is already a disposable, isolated environment, and the venv exists locally to defend against this machine's global Anaconda installation, a hazard that does not exist here. Note in a comment that CI therefore invokes `python` directly while the local commands documented in `backend/README.md` go through `.venv/Scripts/python` — a Linux runner has no `Scripts` directory, so copying the documented command verbatim would fail.
7. Run the backend suite from the `backend` working directory so `pytest.ini` is the rootdir and `app` is importable.
8. Start `uvicorn` in the background, wait for it to bind, then run the two live end-to-end checks: the `/api/health` probe and the WebSocket echo probe, both with `node`, both from the acceptance criteria of plans 02-03 and 02-07. These are the two clauses of the phase gate that only a running server can prove, and they are cheap. Give the wait a bounded retry loop rather than a fixed sleep, and fail with a clear message if the server never binds.
9. Always upload or print `docker compose logs` on failure. A red CI run whose only output is "verify-schema.sh exited 1" costs an hour; the same run with Postgres's init log attached costs a minute.

**Job `frontend`**, on `ubuntu-latest`, running in parallel with no Docker dependency:

1. Check out the repository.
2. Set up Node at the version local development uses, with npm caching keyed on `frontend/package-lock.json`.
3. `npm ci` in `frontend` — `ci` rather than `install`, so the committed lockfile is installed exactly and a transitive-dependency drift fails the build instead of silently entering it.
4. `npm run build`, then `npm test`.

For every action reference, use the `actions/` first-party org and resolve the current major tag at execution time rather than writing a remembered version number. Record the versions used in the SUMMARY. Note in a comment that pinning each action to a full commit SHA is the stronger supply-chain control and is the upgrade path if this repository ever handles anything beyond synthetic demo data.

Do not add a deploy step, a release step, a coverage-reporting service, or a code-scanning action. SENT-1-09's contract is a test runner. Anything more is scope this ticket does not carry (CLAUDE.md Rule 7), and each addition is another third-party action with access to the repository.

  <action>
Replay the `backend-and-policy` job's step sequence locally, in order, from a genuinely cold state, and record the outcome of each step in the SUMMARY. This is the closest available proxy for a real Actions run and it catches ordering bugs — a seed gate running before the schema gate, a policy gate running before OPA has reloaded — that reading YAML does not.

The sequence: `docker compose down -v --remove-orphans`; `docker compose up -d --wait`; `bash infra/health-check.sh`; `bash infra/verify-schema.sh`; `bash infra/apply-seed.sh`; `bash infra/verify-seed.sh`; `docker compose restart opa` followed by `bash infra/health-check.sh opa`; `bash policies/opa-gate.sh`; the backend suite from `backend/`; uvicorn in the background plus the `/api/health` and WebSocket echo probes; and in `frontend/`, `npm ci`, `npm run build`, `npm test`.

Then prove the pipeline can fail, one break at a time, restoring after each. This is the part that turns a green badge into evidence:

- Comment out one `CREATE TABLE` statement in the schema, re-run the cold-start and schema gate, and confirm it exits non-zero naming the missing table.
- Change one Rego threshold constant, re-run the policy gate after restarting OPA, and confirm it exits non-zero naming the affected rule.
- Break one backend test assertion and confirm the backend suite exits non-zero.
- Break one frontend route heading and confirm `npm test` exits non-zero.

Record each break, the failing command, and the exit code in the SUMMARY. If any break does not turn its gate red, that gate is not actually asserting what it claims and must be fixed before this plan closes — a gate that cannot fail is worse than no gate, because it produces confident evidence of nothing.

Note in the SUMMARY the two places where the runner's Linux environment differs from local Windows development, since these are the most likely causes of a workflow that passes locally and fails on the first real run: the Python interpreter path (`backend/.venv/Scripts/python` locally versus the runner's `python`), and shell script line endings, which `.gitattributes` already forces to LF for `*.sh` — confirm that is still in effect with `git check-attr text -- infra/health-check.sh`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| third-party GitHub Action -> repository checkout and runner | Every `uses:` reference executes arbitrary code with access to the workspace and the job token. |
| pull request from a fork -> CI runner | Untrusted branch content executes in the workflow. |
| CI secrets and tokens -> job environment | Anything exposed to a step is exposed to every dependency that step invokes. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-35 | Tampering | third-party action supply chain | high | mitigate | Only `actions/` first-party references are used, and only for checkout and language setup. No coverage reporter, scanner, or deploy action is added. Versions are resolved at execution time and recorded rather than recalled, and the file carries a comment naming full-SHA pinning as the stronger control and its trigger condition. |
| T-02-36 | Information Disclosure | credentials in workflow logs | medium | mitigate | The only credential is a CI-only Postgres password written into a runner-local `.env`. It is not a secret, guards nothing outside the ephemeral container, and is never echoed. `.env` is gitignored, verified live in 01-VERIFICATION.md. No repository secret is referenced by this workflow at all. |
| T-02-37 | Elevation of Privilege | fork pull requests executing with write access | medium | mitigate | GitHub grants fork PRs a read-only token by default on the `pull_request` trigger, and this workflow uses `pull_request` rather than `pull_request_target`, which would run untrusted code with the base repository's permissions. No step requires write access. |
| T-02-38 | Spoofing | a green badge that proves nothing | high | mitigate | This is the realistic failure mode for AI-authored CI: a workflow whose steps cannot fail. Mitigated by Task 2's four deliberate breaks, each of which must turn its gate red before the plan closes, and by CI invoking the same gate scripts developers run rather than a parallel set of assertions. |
| T-02-39 | Denial of Service | a hung container consuming the runner budget | low | mitigate | Both jobs declare `timeout-minutes`, and concurrency cancellation prevents superseded runs from stacking. |
| T-02-SC | Tampering | package-manager installs in CI | high | mitigate | The backend installs only from the pinned `backend/requirements.txt` audited in plan 02-03; the frontend installs with `npm ci` from the committed `package-lock.json`, resolving exactly the tree approved through plan 02-04's legitimacy checkpoint. CI introduces no package that has not already passed the gate. |
</threat_model>
