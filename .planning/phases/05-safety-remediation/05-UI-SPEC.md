# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This phase's UI-facing requirement is UI-02, the Action/Approval Centre (`frontend/src/pages/Actions.tsx`, already scaffolded as a stub, and the `/api/copilot/stream/{session_id}` live push per D-02/REM-04). This contract also covers the "Generate CAPA" A7-trigger control (D-03: an opt-in button on an already-rendered verified finding, not a new page) and the persistent role-selector control (D-01, Claude's Discretion resolved below), since both are load-bearing interaction points for the Approval Centre flow. It does **not** cover `/api/copilot/query` or the chat UI — that is explicitly Phase 6 scope (RESEARCH.md Anti-Patterns, Assumption A4).

**shadcn gate — decision:** No `components.json` exists in this repo, and the stack is React + Vite. Per the shadcn gate this would normally prompt initialization. Declined for this phase: four prior phases (2 through 4) have already shipped a consistent, hand-built Tailwind v4 dark design system with no component library (`AssuranceCard.tsx`, `BlastRadiusPanel.tsx`, `NavBar.tsx`, `PrototypeBanner.tsx`) — introducing shadcn mid-hackathon would fork the design system rather than extend it, and the task brief for this research explicitly instructs staying consistent with what already shipped. `Tool: none` below is a deliberate continuation of the established convention, not an unresolved gap.

## Spacing Scale

Declared values (must be multiples of 4), matching the scale already in production use across `AssuranceCard.tsx`, `BlastRadiusPanel.tsx`, `NavBar.tsx`, `App.tsx`:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-free inline gaps (`mt-1`, `gap-1`), badge micro-padding |
| sm | 8px | Compact element spacing (`mt-2`, nav `gap-1`/`px-2`) |
| md | 16px | Default element spacing (`mt-3`/`mt-4`, card `p-4`) |
| lg | 24px | Section/page padding (`<main className="p-6">` in `App.tsx`) |
| xl | 32px | Reserved — not yet used in shipped pages; available for Approval Centre queue-to-detail layout gaps if a two-column layout is used |
| 2xl | 48px | Reserved — not yet used |
| 3xl | 64px | Reserved — not yet used |

Exceptions (already shipped, carried forward unchanged — not introduced by this phase):
- `py-0.5` (2px) — status/confidence badge vertical padding (`AssuranceCard.tsx` confidence badge)
- `px-3 py-1.5` (12px / 6px) — `NavBar.tsx` nav-pill padding; the persistent role selector (new this phase) should match this exact padding so it reads as the same chrome family, not a new control style

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 (regular, no weight class) | 1.5 |
| Label | 12px (`text-xs`), uppercase, `tracking-wide` | 600 (`font-semibold`) | 1.2 |
| Heading | 18px (`text-lg`) | 600 (`font-semibold`) | 1.2 |
| Display | 24px (`text-2xl`) | 600 (`font-semibold`) | 1.2 |

Two weights only, matching shipped usage: 400 regular (body/paragraph text) and 600 semibold (all headings, section labels, badges). `font-medium` (500) exists only on `NavBar.tsx`'s nav-link active/inactive states, a pre-existing exception scoped to that one component — do not introduce a third weight elsewhere, including the new role selector (match nav-pill styling exactly, inheriting its existing weight).

Mapping for this phase's new elements:
- Page heading "Action / Approval Centre" → Display (already shipped in `Actions.tsx`)
- "Pending Actions", "Generate CAPA" panel titles → Heading
- Status/category badges (PENDING_APPROVAL, APPROVED, REJECTED, EXECUTED, BLOCKED) → Label
- Proposal justification, payload summary, claim/evidence text → Body

## Interaction Notes (non-template, load-bearing for planner/executor)

**Role selector placement (resolves RESEARCH.md Open Question 2):** Persistent app-chrome control, placed adjacent to `NavBar.tsx` (same header row or immediately below it) — not scoped to the Approval Centre page alone. Rationale: the RBAC-gated action that most needs an already-selected role is "Generate CAPA," which lives on the Finding Investigation page (`/findings`, Phase 4), not the Approval Centre — a user must have a role selected before they ever reach `/actions`. Style: same `rounded px-3 py-1.5 text-sm font-medium` pill family as `NavBar.tsx`'s nav links, so it reads as the same chrome, not a new control language. Selecting a role is local client state only (no server round trip); every write-capable request independently attaches the current `user_id`/`role` per request (RESEARCH.md Open Question 1 recommendation: custom headers).

**Approval dialog is data-only, never LLM-authored:** Per REM-03/Bible §11.6, the approval view renders exclusively from the `ActionProposal`/`AuditEvent`-shaped server response fields (`action_type`, `target_system`, `payload`, `justification`, `category`, `status`, timestamps) — the same "props-only, no fetch, no arithmetic, no client-invented fallback" discipline `AssuranceCard.tsx` and `BlastRadiusPanel.tsx` already establish in their file-header comments. Any missing field renders "Not provided" (see UI Considerations `partial` row above) — never a fabricated or paraphrased substitute.

**Reject affordance:** RESEARCH.md Open Question 3 recommends building a reject path alongside approve (same route/audit shape, different terminal status). This UI-SPEC includes Reject Action styling/copy on that recommendation; confirm at plan time that the reject route is in scope before wiring the button live — if descoped, the button should not render rather than dead-end.
