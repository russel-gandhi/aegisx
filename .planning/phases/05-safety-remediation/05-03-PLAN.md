## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> `POST /api/audit/demonstrate-tamper` | An unauthenticated caller can request a deliberate mutation of an audit row |
| Postgres `audit_events` -> `verify_chain` | The read-back path where canonicalisation must match the write path exactly |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-15 | Tampering | `demonstrate_tamper` is a deliberate, reachable audit-mutation endpoint | high | mitigate | The endpoint is required by Bible Section 12 and ROADMAP Phase 5 criterion 5 and cannot be removed. Mitigations: it mutates only `output_summary` to a fixed literal and cannot set an attacker-chosen value; it targets a single `event_id` supplied in the body and affects at most one row; identity is resolved and its invocation is itself logged as a chain link *before* the tamper, so the act is attributable and detectable; and it is the only code path in the repository permitted to mutate an `audit_events` row after insert, stated in its docstring. Residual risk is accepted as an explicit demo requirement, not an oversight. |
| T-05-16 | Repudiation | A false `VERIFIED` verdict from a tamper demo aimed at a nonexistent row | high | mitigate | `demonstrate_tamper` parses asyncpg's command tag and returns `NO_SUCH_EVENT` with `rows_modified: 0` rather than calling `verify_chain` at all; asserted by test. This is the corrected behaviour relative to Bible Section 7.1's own sample. |
| T-05-17 | Tampering | Canonicalisation drift causing untouched rows to report TAMPERED (or, inverted, masking a real break) | high | mitigate | Two named regression tests compare `_canonical_json` computed from the raw asyncpg row against the original event dict, one for JSONB list fields and one for omitted optional fields. |
| T-05-18 | Tampering | Concurrent appends forking the chain after a refactor removes the table lock | medium | mitigate | `test_concurrent_log_events_do_not_fork_the_chain` fires two `log_event` calls through `asyncio.gather` and asserts the chain still verifies. |
| T-05-19 | Denial of Service | `verify_chain` scanning an unbounded `audit_events` table | low | accept | The demo dataset is bounded (Phase 2 seeds zero audit rows; a full demo run produces tens of rows). Pagination or checkpointing would be unjustified infrastructure for a load this deployment does not have, and Phase 7's performance pass (HARD-06) owns any revisit. |
| T-05-20 | Information Disclosure | `GET /api/audit/verify` exposed without RBAC | low | accept | Per D-04 the read surface is deliberately ungated this phase, and the response carries only a status, a count, and an event id — no record contents. |
| T-05-SC | Tampering | npm/pip/cargo installs | high | mitigate | No new package (`hashlib`, `json`, `asyncio` are stdlib; `asyncpg` and `fastapi` are already pinned). |
</threat_model>
