<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Host network → published container ports | Qdrant (6333) has no authentication at all; OPA (8181) exposes the policy decision API. Whatever reaches these ports is fully trusted by the service. |
| Docker Hub registry → local image cache | Two more third-party images execute on the developer workstation with container privileges |
| Debian package mirrors → derived image build | `infra/qdrant/Dockerfile` fetches and installs a package at build time from outside the pinned base image |
| Host filesystem → container bind mount | `./policies` is the deterministic rule bundle every Phase 2+ compliance decision reads |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-10 | Tampering | `./policies` bundle mount | high | mitigate | Mount as `./policies:/policies:ro`. A writable mount would let a compromised OPA container rewrite the Rego rules that produce every deterministic compliance verdict from Phase 2 onward — the exact evidence the C1 verifier is meant to be able to trust. Verified both by grep and by asserting that a write attempt inside the container fails. |
| T-01-11 | Information Disclosure | Qdrant 6333 and OPA 8181 published ports | medium | mitigate | Publish both as `127.0.0.1:<port>:<port>`. Qdrant ships with no authentication whatsoever, so a bare `6333:6333` would expose the entire vector store to the LAN/VPN (RESEARCH.md Pitfall 4). Qdrant's gRPC port 6334 is deliberately not published at all. OPA's `--addr=0.0.0.0:8181` is container-internal; host exposure remains loopback-only. |
| T-01-SC | Tampering | `infra/qdrant/Dockerfile` build-time `apt-get install curl` | medium | mitigate | The derived image builds `FROM qdrant/qdrant:v1.19.0`, whose provenance RESEARCH.md verified by reading the vendor's own Dockerfile in the `qdrant/qdrant` namespace. `--no-install-recommends` limits the added surface to curl and its direct dependencies, and the apt lists are removed in the same layer. This phase installs no npm, pip, or cargo package, and RESEARCH.md's Package Legitimacy Audit returned no `[ASSUMED]` and no `[SUS]` entry, so no blocking-human legitimacy checkpoint is required. |
| T-01-12 | Tampering | `openpolicyagent/opa` and `qdrant/qdrant` image pulls | medium | mitigate | Exact tag pins per D-04, never a floating tag (gated by a zero-count grep on the Compose file). Both namespaces are the vendors' own and were verified against their published build sources in RESEARCH.md's Package Legitimacy Audit. |
| T-01-13 | Elevation of Privilege | Derived Qdrant image runtime user | medium | mitigate | The Dockerfile restores exactly the base image's configured `Config.User` after the install layer, determined by inspecting the base image rather than assumed. If the vendor image declares no user, no `USER` instruction is added — the derived image introduces no privilege delta either way. |
| T-01-14 | Spoofing | OPA decision API on 8181 | low | accept | OPA is deployed unauthenticated on loopback, matching the Bible's sidecar architecture where the FastAPI backend is the only caller. Adding authentication between two processes on the same host would not raise the security floor while the port is loopback-bound, and the deterministic-first design depends on this call being cheap and always available. Revisit if the sidecar is ever exposed beyond localhost. |
</threat_model>
