<objective>
Close the phase by proving the two claims that no single-service check can prove: that the stack really does come up from nothing on one command, and that developer data survives a normal stop (D-05).

Purpose: up to this point every service was verified on a warm machine, with images already pulled, volumes already initialised, and containers already created. ENV-01's actual promise — "`docker-compose up -d postgres qdrant opa` is the only setup step" — is a claim about a cold machine. This plan destroys the state and re-earns it. It also converts D-05 from a Compose declaration into a tested behavior, and writes down the `down` versus `down -v` seam that the Stage 6 demo-reset ticket (SENT-6-06) will act on.

Output: `infra/verify-persistence.sh` and `infra/README.md`.

Ordering inside the plan is deliberate: the non-destructive persistence proof runs first, the destructive cold-start gate second. Reversing them would destroy the volumes the persistence test needs.
</objective>

  <action>
    Write `infra/verify-persistence.sh`, an automated assertion for D-05. Unlike `infra/health-check.sh`, this script deliberately does mutate the environment — it stops and restarts the stack — so it must say so in a header comment and must clean up after itself.

    Shape and behavior:
    - Shebang `#!/usr/bin/env bash`, `set -uo pipefail`, `cd` to the repo root derived from the script's own location.
    - Reuse the same `dc()` wrapper as `infra/health-check.sh`: run `docker compose "$@"` when `docker compose version` exits 0, else `docker-compose "$@"`.
    - Register a cleanup trap on EXIT that drops the Postgres probe table and deletes the Qdrant probe collection, so a failed run does not leave residue that later pollutes the seeded demo state SENT-1-02 creates.
    - Read `POSTGRES_USER` and `POSTGRES_DB` from the environment with the same defaults the Compose file uses (`sentinel` for both).
    - Step 1 — write probes. Postgres: `dc exec -T postgres psql -v ON_ERROR_STOP=1 -U "$PGUSER" -d "$PGDB" -c "CREATE TABLE IF NOT EXISTS gsd_persistence_probe (id int primary key); INSERT INTO gsd_persistence_probe VALUES (1) ON CONFLICT DO NOTHING;"`. Qdrant: run curl *inside* the qdrant container — `dc exec -T qdrant curl -fsS -X PUT http://localhost:6333/collections/gsd_persistence_probe -H 'content-type: application/json' -d '{"vectors":{"size":4,"distance":"Cosine"}}'`. Running the client in-container both sidesteps Windows Git Bash curl quirks and exercises the derived image built in plan 01-03.
    - Step 2 — cycle the stack. `dc down` with no `-v`. This is the whole point of the test: `down` must not touch the volumes. Then `dc up -d --wait --wait-timeout 180 postgres qdrant opa`.
    - Step 3 — re-read and assert. Postgres: `SELECT count(*) FROM gsd_persistence_probe;` must return 1. Qdrant: `dc exec -T qdrant curl -fsS http://localhost:6333/collections/gsd_persistence_probe` must succeed, meaning the collection still exists. If either read fails, print which one and exit 1.
    - Step 4 — re-assert health by calling `bash infra/health-check.sh`, so a passing persistence run also confirms the stack came back green.
    - Print `PERSISTENCE OK` and exit 0 only when every assertion passed; otherwise print `PERSISTENCE FAILED` with the failing step and exit 1. Never substitute a fallback value for a failed lookup and then compare it — that produces a gate that passes while measuring nothing.
    - Register the file executable with `git update-index --add --chmod=+x infra/verify-persistence.sh`.

    Run the script and confirm it passes. If the Qdrant collection does not survive, the mount path in the Compose file is wrong (Qdrant's storage lives at `/qdrant/storage`) — fix the mount, not the test.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Test probe writes → shared dev data stores | The persistence test writes real rows and collections into the same Postgres and Qdrant instances Phase 2 will seed |
| Destructive operator commands → named volumes | `down -v` is a single flag away from `down` and destroys all developer and demo state |
| Host filesystem → container | The persistence probe runs client binaries inside containers rather than on the host |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-15 | Tampering | Postgres and Qdrant dev data | medium | mitigate | `infra/verify-persistence.sh` namespaces its artifacts as `gsd_persistence_probe` and removes both in an EXIT trap that fires on failure as well as success; the task's acceptance criteria re-query both stores afterwards to prove no residue survives into the SENT-1-02 seed set. |
| T-01-16 | Denial of Service | `postgres_data` and `qdrant_data` volumes | medium | mitigate | The destructive `down -v` gate runs exactly once, at the only point in the project where there is provably nothing to lose (no schema and no seed data land until Phase 2), and the ordering constraint is encoded as Task 2's precondition. `infra/README.md` then documents the `down` versus `down -v` distinction as its own section so the flag is never typed accidentally later, and points at SENT-6-06 as the supported restore path. |
| T-01-17 | Repudiation | Certified image versions | low | mitigate | The resolved `sha256:` digests of all three images are recorded in `infra/README.md` at the moment the environment was verified, so a later "it worked on Phase 1" claim can be checked against the exact bits rather than against a mutable tag. |
