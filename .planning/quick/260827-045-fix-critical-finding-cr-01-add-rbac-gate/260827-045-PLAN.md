<objective>
`POST /api/audit/demonstrate-tamper` performs a real row `UPDATE` against
`audit_events` but is gated only by `require_identity`, which accepts all three
Bible-defined roles. The read-only Auditor role can therefore corrupt the audit
chain -- the one subsystem whose entire purpose is tamper-evidence. Every other
write-capable route in this phase (`routes/actions.py`) enforces `check_rbac`
first. This is Critical finding CR-01 from `.planning/phases/05-safety-remediation/05-REVIEW.md`.

Fix: gate the route with the same `check_rbac` call `routes/actions.py` uses, so
only IT System Manager may invoke the tamper demo, and prove the denial with tests.

Purpose: close a real authorization hole on the audit trail, and close it in the
way the codebase already expresses authorization, so there is exactly one source
of role authority rather than two that can drift.

Output: one guard clause plus a docstring correction in `backend/app/routes/audit.py`,
and denial coverage for both non-IT-System-Manager roles in
`backend/tests/test_routes_audit.py`.

## Design decisions and why

**Use `check_rbac(identity.role, "A7")`, not a role-name comparison.**
05-REVIEW.md's suggested fix is a literal `identity.role != "IT System Manager"`
comparison inside the route. That produces the right behavior but violates an
invariant `c2_gateway.py`'s own module docstring states explicitly: `PERMISSION_MATRIX`
is the single place role authority exists in the codebase, and no route keeps a
second copy. A hardcoded role name in a route IS a second copy -- one that will
not move if the matrix ever does. `check_rbac(identity.role, "A7")` yields the
identical allow/deny split (IT System Manager holds A7; QA/Compliance is denied
A7 by design; Auditor holds only A1/A2) while keeping the matrix authoritative.
The task brief asks for the `check_rbac` pattern for this reason; the review's
inline snippet is the finding's illustration, not its required shape.

**Why A7 and not some new capability.** No new matrix entry is added. Adding a
capability id would be a schema change to the transcribed-verbatim Bible
permission matrix, which is out of scope for a surgical authorization fix (Rule 7,
no silent scope expansion). A7 is used because it is the existing capability whose
holder set is exactly the intended allow set, and the route comments say so.

**Deny before the pool, deny before the log.** A rejected attempt writes nothing:
no `TAMPER_DEMO_INVOKED` row, no chain append. This matches `generate_capa`, which
returns 403 before touching Postgres. Auditing denied attempts would need a new
`action_type` and a DB round trip on the rejection path, which is a separate
decision, not part of closing CR-01 -- the route comment records that the omission
is deliberate so a later reviewer does not read it as the same class of oversight
CR-01 itself was.

**Allow-path coverage already exists and stays untouched.**
`test_demonstrate_tamper_unknown_event_id_returns_no_such_event` and
`test_demonstrate_tamper_endpoint_reports_tampered` both drive the route with
`IT_MANAGER_HEADERS` and assert a 200 outcome. They are the assertion that IT
System Manager can still successfully invoke the endpoint. They must pass
unmodified after this change; if either needs editing to stay green, the gate was
placed wrong.
</objective>
