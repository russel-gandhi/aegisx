<objective>
`GET /api/systems/{system_id}/assurance-cards` re-narrates every failing compliance
check through the LLM on every single request. A live session burned 811 Gemini
requests (~2.59% success, confirmed in Google's console) for what amounted to 2-3
distinct findings' worth of text, because page loads, system switches and re-renders
each replay the same narration from scratch.

Fix: memoize the narration step itself, content-addressed on the exact prompt.

Purpose: stop paying an API request for a sentence that was already generated from
byte-identical inputs, without ever letting a stale sentence outlive the record it
describes and without letting any deterministic verdict be served from memory.

Output: a small in-process cache module, a three-line wiring change inside
`narrate_gap()`, test isolation for the module-global state it introduces, and
coverage proving the invalidation boundary holds.

## Design decisions and why

**Cache inside `narrate_gap()`, not inside the route.** `narrate_gap` has three call
sites: `run_a2` (the LangGraph node), `routes/findings.py::get_assurance_cards`, and
`routes/actions.py::_find_finding_server_side`. That last one is the quiet amplifier —
it re-derives findings server-side by narrating *every* failing check until one
matches the requested `finding_id`, so a single `generate-capa` POST costs up to one
LLM call per failing check. Placing the memo in the route would fix one of three call
sites and leave the worst one untouched.

**Key = digest of the exact prompt string.** `narrate_gap` builds its prompt from the
check name, its description, `record_id`, `rule_id`, and `record!r`. Hashing the
finished prompt puts every one of those inside the key by construction — an edited
record produces a different prompt, a different key, and a miss. There is no TTL and
no invalidation routine to keep in sync with the prompt template, because staleness is
structurally impossible rather than merely unlikely. If a later plan adds a field to
the prompt, the key tracks it automatically.

**Why NOT `evidence_graph.py`'s rebuild/read-split pattern.** That split exists (D-02)
because `graph_nodes`/`graph_edges` are *snapshot* caches: they hold a copy of domain
state that genuinely can drift, so a human-triggered rebuild endpoint is the
invalidation mechanism. Narration is content-addressed — the key *is* the input — so
there is nothing to invalidate and a rebuild endpoint would be a control with no job.
A Postgres table would also require a schema change, and the schema is closed
(CLAUDE.md Rule 7). The simpler pattern is not a shortcut here; it is the stricter one.

**In-process, bounded, LRU.** Single uvicorn process for this demo. Worst case on
restart is one re-narration per distinct finding. Under multiple workers each worker
would keep its own copy — still correct, just less effective; recorded, not built for.

**Degraded responses are NOT cached.** When the router degrades, `narrate_gap` returns
its deterministic template sentence. Caching that would latch a provider outage into
memory for the lifetime of the process — the endpoint would keep serving fallback text
long after the provider recovered. The degraded path costs nothing anyway: with no key
configured the router fails before any HTTP request is built.

**No in-flight de-duplication.** Two concurrent requests for the same cold key can
both call the provider. Fixing that needs a module-level `asyncio.Lock`, and a
module-level asyncio primitive is bound to the loop that created it — the exact
failure mode `conftest.py` documents at length for asyncpg pools under this suite's
`asyncio.run()`-per-test convention. Sequential repeats are the dominant cost here.
Accepted, deliberately, not overlooked.

**Identical prompts across different systems share an entry.** A check whose `record`
is `None` builds a prompt containing no system identifier, so two systems that both
lack a URS document hit the same key. That is correct dedup, not leakage: nothing
system-specific is in the prompt, so nothing system-specific can come out. `finding_id`,
`evidence_ids` and `confidence` are all computed per-system outside the cache.

**`model_attribution` stays honest.** The cache stores `(text, model_id)` together, so
a card built from a cache hit still names the model that actually authored the
sentence. Attributing cached text to a cache rather than to its author would be the
inaccurate option; the sentence really was produced by that model.

**Explicitly NOT touched** (deliberate, not oversight):
- `app/agents/minimal_specialists.py::_narrate_gap` and `app/agents/a7_remediation.py` —
  separate narration functions. A7's CAPA text is generated once per proposal by an
  explicit POST, not replayed by a GET. Out of the declared scope.
- `verify_finding()` / C1 / OPA / any `passed` boolean — never cached, in any form.
  This is the product thesis (CLAUDE.md), and Task 2 proves it rather than asserting it.
- The pre-existing OPA-corroboration test failures documented in
  `.planning/phases/05-safety-remediation/deferred-items.md`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Postgres row contents -> LLM narration prompt -> process memory | Record fields already cross into the prompt today; this plan additionally retains the resulting sentence in the process heap |
| backend -> external LLM provider APIs | Outbound only; unchanged by this plan except that fewer requests cross it |
| cached narration -> HTTP response body -> auditor's screen | A GxP-relevant surface: a sentence rendered on an Assurance Card must describe the record as it is now |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-quick-01 | Tampering | narration served for a record that has since changed | high | mitigate | The key is a digest of the finished prompt, so every field reaching the model is inside it by construction — an edited record cannot collide with its pre-edit entry. Enforced by Task 2's per-field mutation tests and the Postgres UPDATE round-trip, not by inspection. |
| T-quick-02 | Tampering | a compliance verdict served from memory | critical | mitigate | The cache stores a two-string pair and nothing else, and `app/narration_cache.py` imports nothing from `app.*` — it structurally cannot reach `verify_finding`, OPA or a `passed` boolean. Enforced by Task 1's import grep gate and Task 2's OPA-unreachable test, which proves grades flip on a full cache hit. |
| T-quick-03 | Denial of Service | unbounded growth of the in-process map | medium | mitigate | Bounded at 256 entries with least-recently-used eviction. The demo corpus produces findings in the low tens, so the bound exists to make growth impossible rather than to manage it. |
| T-quick-04 | Information Disclosure | record field values retained in process memory | low | accept | The retained sentence is the same text the request would have produced without a cache, held in the same process that already holds the rows. Nothing is persisted, logged, or written to a new store. Cross-system key sharing occurs only when prompts are byte-identical, which by definition means the prompt contains no system-specific content. |
| T-quick-05 | Repudiation | provenance of a cached sentence | medium | mitigate | `model_id` is stored and returned alongside the text, so `model_attribution` continues to name the model that actually authored the sentence rather than being blanked or relabelled. |
| T-quick-06 | Denial of Service | a provider outage latching into the cache | medium | mitigate | Degraded router results are never stored, so recovery is immediate. Proven by Task 2's outage test, which narrates keyless then keyed and asserts real model text on the second pass. |
| T-quick-SC | Tampering | npm/pip/cargo installs | n/a | n/a | No package is installed or upgraded. `hashlib` and `collections` are standard library. No package-legitimacy gate applies. |
